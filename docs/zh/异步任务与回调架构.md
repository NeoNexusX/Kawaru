# 异步任务与回调架构

本文档介绍 Kawaru 的异步任务系统（Celery）和外部服务回调机制（Aliyun FC）。配套架构图见下方链接。

## 1. 为什么需要异步任务

Kawaru 的核心业务（文件解包、算法处理、聚类分析、预览图生成）都在阿里云函数计算（FC）上执行，不占用后端服务器资源。这些任务耗时从几秒到几分钟不等，不能让用户同步等待。Celery 作为任务队列，负责把任务从 API 传递给 Worker，再由 Worker 触发 FC 执行。

此外，邮件发送、定时清理等辅助操作也走 Celery 异步执行。

## 2. Celery 运行时拓扑

> [打开交互式架构图：Celery 异步任务架构](../frameworkmap/kawaru-celery-async.html)

### 2.1 组件角色

| 组件 | 角色 | 说明 |
|------|------|------|
| FastAPI 应用 | 任务生产者 | 通过 `delay()` 投递任务到 Redis Broker |
| Redis Broker | 消息队列（DB1） | 存储待执行的任务消息 |
| Redis Backend | 任务结果（DB2） | 存储任务执行结果 |
| Redis RedBeat | 调度元数据（DB3） | 存储定时任务调度信息和分布式锁 |
| Celery Worker | 任务执行器 | 消费 Broker 中的任务并执行 |
| Celery Beat | 定时调度器 | 按配置的时间间隔投递定时任务到 Broker |

### 2.2 Redis DB 分层

Redis 使用四个独立的数据库（DB index），避免不同类型的数据互相干扰：

| DB | 用途 | 典型 key |
|----|------|---------|
| DB0 | 会话、验证码、限流、访问计数 | `login_token:*`、`email_code:*`、`stats:all:*` |
| DB1 | Celery Broker（任务消息队列） | Celery 内部管理 |
| DB2 | Celery Backend（任务结果） | Celery 内部管理 |
| DB3 | RedBeat 调度元数据 + 分布式锁 | RedBeat 内部管理 |

### 2.3 任务执行流程

```
API 调用 delay() → 任务进入 Redis Broker（DB1）
    ↓
Worker 从 Broker 消费任务
    ↓
Worker 执行任务（触发 FC / 发邮件 / 清理文件）
    ↓
任务结果写入 Redis Backend（DB2）
```

## 3. 任务分类

### 3.1 FC 触发任务（6 种）

这些任务由 Worker 通过 HTTP 请求触发对应的 FC 函数：

| 任务 | 对应 FC | 用途 | 所属业务 |
|------|--------|------|---------|
| `fc-algorithm` | fc-algorithm | 算法管线处理（PeakPick/Normalize/Align/NoiseReduce/Baseline） | 文件处理 |
| `fc-raw-convert` | fc-raw-convert | imzML 直转 Zarr（无算法） | 文件处理 |
| `fc-clustering` | fc-clustering | UMAP/KMeans 聚类 | 文件处理 |
| `fc-tic` | fc-tic | TIC 预览图生成 | 上传后预览 |
| `fc-feature` | fc-feature | UMAP 预览图生成 | 上传后预览 |

### 3.2 邮件与外部校验任务

| 任务 | 用途 |
|------|------|
| `send_smtp_email_task` | 通过 SMTP 发送验证码邮件 |
| `validate_orcid_task` | 异步校验 ORCID 身份真实性 |

### 3.3 定时任务（Beat 调度）

| 任务 | 频率 | 用途 |
|------|------|------|
| `heartbeat` | 每 67 秒 | Worker 保活心跳 |
| `cleanup_source_zips` | 定时 | 删除超过保留期的上传源 ZIP（下载只走 imzML/ibd） |
| `cleanup_stale_preflights_all_users` | 定时 | 清理过期的预检记录 |
| `cleanup_failed_experiments` | 定时 | 清理失败的处理记录 |
| `cleanup_stale_process_runs` | 定时 | 巡检超时的处理任务，标记为 failed |

### 3.4 OSS 操作（不经过 Celery）

OSS 操作由 `OssStorage`（`storage/oss/oss_storage.py`）在调用方进程内直接执行，不投递 Celery 任务，也不轮询结果，API 请求链路不依赖 Worker：

| 操作 | 实现方式 |
|------|------|
| 签发上传 / Zarr 只读 STS 临时凭证 | STS SDK 异步接口 `assume_role_async` |
| 检查对象存在性和大小、打标签、删除对象 | OSS 异步客户端 |
| 签名下载 URL | 本地签名计算，不发网络请求 |

单次调用的等待上限沿用配置 `oss_default_timeout_seconds`，删除使用 `oss_delete_object_timeout_seconds` / `oss_delete_prefix_timeout_seconds`。

## 4. FC 调用与回调流程

> [打开交互式架构图：Aliyun FC 回调架构](../frameworkmap/kawaru-fc-callback.html)

### 4.1 调用与回调的完整流程

```
API 投递任务 → Worker 消费 → HTTP 触发 FC 函数
                                    ↓
                              FC 执行计算
                                    ↓
                              FC 回调 API（POST /callback/*）
                                    ↓
                              API 更新数据库状态
```

FC 是异步执行的：Worker 只负责触发，不等待 FC 执行完成。FC 执行完后通过 HTTP 回调通知 API 结果。

### 4.2 回调端点

**5 个 POST 回调（业务结果通知）：**

| 回调端点 | 触发方 | 做什么 |
|---------|--------|--------|
| `oss_upload_callback` | 解包 FC | 上传解包完成，创建 Origin 记录 |
| `algorithm_callback` | 算法 FC | 算法处理或直转完成，更新 Run 状态和配额 |
| `tic_callback` | TIC FC | TIC 预览图生成完成，写入 image_path |
| `umap_callback` | UMAP FC | UMAP 预览图生成完成，写入 image_path |
| `clustering_callback` | 聚类 FC | 聚类完成，更新 clustering_status |

**2 个 GET 辅助端点：**

| 端点 | 用途 |
|------|------|
| `get_expected_hash` | FC 请求文件 MD5 校验码，用于验证文件完整性 |
| `config` | FC 获取系统配置（如 OSS 路径等） |

## 5. 回调安全边界

### 5.1 Token 鉴权

所有 FC 回调请求必须在 `X-FC-Token` 头中携带 `FC_CALLBACK_TOKEN`。API 通过路由级依赖 `verify_fc_callback_token` 验证 Token 是否匹配。Token 不匹配则返回 401。

### 5.2 对象存在性校验

各回调的实际行为不完全相同：

| 回调 | 对象校验和缺失时行为 |
|------|------------------------|
| `oss_upload_callback` | 校验 ZIP 大小以及 imzML/ibd 是否存在；异常时将 File/Origin 标记为 failed 并返回 5xx |
| `algorithm_callback` | 校验 Zarr 目录；对象缺失时将 Run 标记为 failed，然后正常返回 |
| `tic_callback` / `umap_callback` | 校验预览图目录；缺失时只记日志并正常返回，不写 `image_path` |
| `clustering_callback` | 结果写回已有 Zarr，回调本身不做独立对象存在性校验 |

### 5.3 重复回调保护

| 回调 | 幂等方式 |
|------|---------|
| algorithm_callback | 串行重复成功回调会在读到 completed 后返回；当前不是条件 UPDATE，并发重复回调仍存在重复累加配额的窗口 |
| clustering_callback | 当前无终态保护；成功和失败回调都会写入 `clustering_status`，后到回调可覆盖先到结果 |
| tic/umap callback | 当前没有基于 `image_path` 的早返回；重复成功回调会再次写入 |
| oss_upload_callback | 已存在任意 Origin 记录时直接返回，不重复创建 |

## 6. 状态更新和事务边界

回调并未共享一套统一的状态转换原语。Algorithm 成功回调会先读状态，然后更新 Run、通过数据库原子加法累加 `processed_file_size`，并在同一事务提交；但“先读后写”本身不能关闭并发重复回调窗口。`GREATEST` 用在配额退还的原子减法中，不是成功回调的幂等门控。

## 7. 幂等、迟到回调与重复回调

| 场景 | 处理方式 |
|------|---------|
| FC 重试导致串行重复成功回调 | Algorithm 回调读到 completed 后跳过，配额通常只计一次 |
| Algorithm 并发重复成功回调 | 存在两个请求都读到非 completed 并重复计费的竞态窗口 |
| 超时误判后的迟到成功回调 | 可从 FAILED 翻转为 COMPLETED |
| 重复失败回调 | Algorithm 只在 processing 时落 failed；Clustering 当前无同等保护 |
| FC 崩溃或消息丢失 | 由 `cleanup_stale_process_runs` 超时兜底标 FAILED |

## 8. 失败处理和重试责任

后端没有为回调请求建立单独的重试队列。FC 端是否会因 HTTP 返回码重试、重试次数及告警策略由仓库外的 FC 实现和部署配置决定，不能从当前后端代码保证。当前回调的主要 HTTP 结果也不是一致的：

| 返回码 | 含义 | FC 行为 |
|--------|------|---------|
| 200/204 | 处理成功，或部分回调将业务失败落库/记日志后正常返回 |
| 400 | Algorithm/Clustering 目标 Run 不存在等参数错误 |
| 404 | 部分文件或预览回调的目标记录不存在 |
| 5xx | 上传回调校验失败、数据库或其他未处理异常 |

## 9. 可观测性与排查入口

| 排查场景 | 查看方式 |
|---------|---------|
| 任务是否投递成功 | 查看 Redis Broker（DB1）中的任务消息 |
| Worker 是否正常消费 | `celery -A celery_runtime.entrypoint:celery_app inspect ping` |
| 任务执行结果 | 查看 Redis Backend（DB2）或应用日志 |
| 定时任务调度 | 查看 Redis RedBeat（DB3）中的调度元数据 |
| FC 是否触发成功 | 查看 Worker 日志中的 HTTP 请求记录 |
| 回调是否到达 | 查看 API 日志中的回调处理记录 |
