# 系统部署与数据库演进架构

本文档介绍 Kawaru 的部署拓扑、CI/CD 流水线和数据库迁移机制。配套架构图见下方链接。

## 1. 系统运行环境概览

Kawaru 使用 Docker Compose 部署，所有应用容器共享同一份 `.env` 和配置文件。dev 和 prod 各自独立一台服务器，互不影响。

| 环境 | 服务器目录 | Compose 项目名 | 镜像标签 |
|------|-----------|---------------|---------|
| dev | `/opt/kawaru-dev` | `kawaru-dev` | `dev-latest` / `dev-<sha>` |
| prod | `/opt/kawaru-prod` | `kawaru-prod` | `latest` / `sha-<sha>` |

## 2. Docker Compose 服务拓扑

> [打开交互式架构图：Docker 部署架构](../frameworkmap/kawaru-docker-deploy.html)

系统由 6 个容器组成：

| 容器 | 角色 | 说明 |
|------|------|------|
| `migrate` | 一次性 Schema 迁移 | 启动时执行数据库迁移，成功后退出，其余容器等待它完成后才启动 |
| `app` | FastAPI API 服务 | 监听 :8000，对外提供 HTTP 接口 |
| `worker` | Celery Worker | 异步任务执行器，10 个线程 |
| `beat` | Celery Beat | 定时任务调度器，使用 RedBeat（基于 Redis 的分布式调度） |
| `mariadb` | MariaDB 11.4 | 业务数据库，端口 13306 |
| `redis` | Redis 8.4 | 缓存 + 消息队列，AOF 持久化，端口 16379 |

启动顺序：`.env` + `config.yaml` → `migrate`（必须成功）→ `app` + `worker` + `beat`（并行启动）

数据库端口绑定策略：

| 环境 | MariaDB/Redis 端口 | 说明 |
|------|-------------------|------|
| dev | `0.0.0.0:13306/16379` | 公开暴露，便于外部工具连接调试 |
| prod | `127.0.0.1:13306/16379` | 仅回环绑定，不对公网开放，需 SSH 隧道访问 |

数据持久化：MariaDB 数据、Redis AOF 和应用日志通过 bind mount 挂载到宿主机 `data/` 目录，容器重建不丢数据。业务文件全部存 OSS，不占宿主机磁盘。

## 3. CI/CD 完整流程

> [打开交互式架构图：CI/CD 流水线](../frameworkmap/kawaru-cicd-pipeline.html)

### 3.1 CI 流水线（PR 检查）

触发条件：向 `test` 分支提交 PR 或 push 代码。

```
触发 CI → 迁移检查 → 静态检查 → [PR 到此结束] / [push/手动 → 构建镜像 → 推送 GHCR → 集成测试]
```

| 阶段 | 内容 |
|------|------|
| 迁移检查 | 在临时 MariaDB 上执行 check-heads、upgrade、verify、alembic check，验证迁移脚本正确性 |
| 静态检查 | compileall 语法检查 + ruff lint（当前不阻塞） |
| 构建镜像 | 仅 push/手动触发时执行，构建 Docker 多阶段镜像 |
| 推送 GHCR | 测试镜像标签为 `kawaru:test-<sha>` |
| 集成测试 | 拉取测试镜像，compose 起栈后运行 pytest |

**关键规则**：PR 不构建镜像，只做迁移检查和静态检查。push 到 `test` 或手动触发才构建并跑集成测试。

### 3.2 CD 流水线（自动部署）

触发条件：push 到 `dev` 或 `main` 分支。

```
Push → 构建镜像 → 推送 GHCR → SSH 到服务器 → 拉取镜像 → 备份数据库 → 执行迁移 → 启动服务
```

| 步骤 | 说明 |
|------|------|
| 构建并推送 | dev 推送 `dev-latest` + `dev-<sha>`；main 推送 `latest` + `sha-<sha>` |
| SSH 部署 | 服务器按对应 SHA 标签拉取镜像，避免浮动标签漂移 |
| 数据库备份 | dev 保留 7 天，prod 保留 30 天 |
| 执行迁移 | `python -m database.migration upgrade` |
| 启动服务 | `compose up -d app worker beat` |
| 清理旧镜像 | 删除 7 天前的本地旧镜像 |

**关键规则**：CD 独立由分支 push 触发，不依赖 CI 是否通过。部署失败时自动输出所有服务的状态和日志摘要。

## 4. 数据库迁移架构

> [打开交互式架构图：数据库迁移架构](../frameworkmap/kawaru-db-migration.html)

### 4.1 迁移引擎

系统使用 Alembic 管理数据库 Schema 变更。迁移脚本存放在 `migrations/versions/` 目录，每个脚本有唯一的 revision 编号，串联成一条单向版本链。

| CLI 命令 | 用途 |
|---------|------|
| `check-heads` | 检查是否存在多个 Alembic head（分叉检测） |
| `upgrade` | 升级数据库到最新版本 |
| `verify` | 验证数据库当前版本是否与代码 head 一致 |
| `stamp-baseline` | 对已有存量数据库打上基线版本标记 |

### 4.2 安全机制

| 机制 | 说明 |
|------|------|
| 顾问锁 | `upgrade` 和 `stamp` 执行时通过 MariaDB `GET_LOCK()` 获取命名锁，防止多实例并发迁移 |
| Schema Guard | 应用启动时只校验数据库版本是否匹配，不主动执行迁移。版本不匹配则拒绝启动 |
| 非空未版本化拦截 | 数据库有表但没有 `alembic_version` 记录时，拒绝迁移，防止误操作 |

### 4.3 migrate 容器与应用启动顺序

```
migrate 容器（one-shot）
  ↓ 成功
app + worker + beat（并行启动；app 的 lifespan 再通过 Schema Guard 校验版本）
  ↓ 版本不匹配
启动失败，旧版本服务继续运行
```

应用容器通过 Compose 的 `condition: service_completed_successfully` 等待 migrate 完成。worker 和 beat 的独立入口不运行 Schema Guard，它们依赖 migrate 容器这道启动门禁；app 还会在 FastAPI lifespan 中复核版本。migrate 失败时，app/worker/beat 不会启动，旧版本服务不受影响。

## 5. dev/prod 差异

| 维度 | dev | prod |
|------|-----|------|
| 触发分支 | `dev` | `main` |
| 镜像标签 | `dev-latest` + `dev-<sha>` | `latest` + `sha-<sha>` |
| 并发抢占 | `cancel-in-progress: false`（不中断发布） | `cancel-in-progress: false`（不中断发布） |
| DB/Redis 端口 | 公开暴露 | 仅回环绑定 |
| 备份保留 | 7 天 | 30 天 |

## 6. 部署失败点与恢复策略

| 失败场景 | 影响 | 恢复方式 |
|---------|------|---------|
| migrate 失败 | app/worker/beat 不启动，旧版本继续运行 | 修复迁移脚本后重新发布 |
| 镜像拉取失败 | 新版本不启动 | 检查 GHCR 凭证和网络 |
| 数据库连接失败 | 所有服务不可用 | 检查 .env 中的数据库密码和 MariaDB 容器状态 |
| Redis 连接失败 | 异步任务不可用，登录态丢失 | 检查 Redis 容器状态 |

## 7. 配置文件索引

| 文件 | 用途 | 存放位置 |
|------|------|---------|
| `.env` | 环境变量（密钥、密码、路径） | 服务器 `/opt/kawaru-{env}/` |
| `{env}-config.yaml` | 应用配置（数据库连接、OSS、FC） | 服务器 `/opt/kawaru-{env}/` |
| `docker-compose.{env}.yml` | Compose 编排文件 | CD 自动同步到服务器 |
| `alembic.ini` | Alembic 静态配置 | 仓库根目录 |
