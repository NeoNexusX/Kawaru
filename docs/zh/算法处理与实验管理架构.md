# 算法处理与实验管理架构

本文档介绍 Kawaru 的算法处理任务和数据管理体系，包括处理任务的三条路径、数据关联关系和结果访问方式。配套架构图见下方链接。

## 1. 处理系统的业务目标

上传完成的 imzML 文件可以发起算法处理，由 FC 转换为 Zarr 格式并执行预处理算法，前端再基于结果做聚类分析和可视化。后端只负责校验、调度和状态管理：

- 校验处理配额、文件归属和文件状态
- 创建运行记录（Run）并异步触发 FC
- 接收 FC 回调，维护 Run 状态并累加处理配额
- 签发只读凭证，让前端直读 Zarr 结果
- 巡检超时任务，清理已删除的结果对象

## 2. 核心领域对象

> [打开交互式架构图：数据与处理管理架构](../frameworkmap/kawaru-experiment-management.html)

### 2.1 数据关联关系

```
FileInDB（用户上传的文件）
    ↓
OriginImzML（FC 解包后的 imzML + ibd）
    ↓
ProcessRun（算法处理/直转/聚类的运行记录）
```

| 对象 | 说明 | 关键字段 |
|------|------|---------|
| FileInDB | 用户上传的文件记录 | file_id, status, size, path |
| OriginImzML | FC 解包后的原始数据 | origin_id, file_id, imzml_path, ibd_path |
| ProcessRun | 一次处理任务的运行记录 | run_id, experiment_id, source_file_id, status, output_size |
| DataCollection | 文件集合（实验分组） | collection_id, user_id, 成员列表 |

### 2.2 级联删除规则

- 删除文件 → 级联删除所有 Origin 和关联的 Run
- 删除 Run → 清理 OSS 上的 Zarr 结果目录，退还处理配额
- 删除直转 Run → 同时解除文件与默认直转结果的关联

## 3. 处理任务主链路

> [打开交互式架构图：处理任务架构](../frameworkmap/kawaru-processing-pipeline.html)

### 3.1 通用流程

```
前端提交处理请求 → API 校验（JWT + 配额 + 归属 + 文件状态）
    ↓
创建 Run 记录，写入数据库
    ↓
提交事务后投递 Celery 任务
    ↓
Worker 消费任务，HTTP 触发 FC
    ↓（API 立即返回 run_id，不等 FC 完成）
FC 执行计算，写入 Zarr 到 OSS
    ↓
FC 回调 API，校验对象存在性后更新 Run 状态
    ↓
前端轮询状态，获取 Zarr 只读凭证
```

### 3.2 关键规则

- 只有 `completed` 的文件才能发起处理
- 创建接口立即返回 run_id，任务是否成功以数据库状态为准
- 处理配额在创建时检查，按累计输出大小限制
- 当前算法处理和直转创建都以 `allow_public=True` 获取 Origin：任何登录用户都可对公开文件发起任务
- 公开文件的直转结果可被任何登录用户读取；普通算法 Run 仍只能由 Run 创建者或管理员读取

## 4. 算法处理、直转和聚类的差异

| 维度 | 算法处理 | 直转 | 聚类 |
|------|---------|------|------|
| 接口 | `POST /processes` | `POST /processes/raw-convert` | `POST /processes/{run_id}/clustering` |
| 对应 FC | fc-algorithm | fc-raw-convert | fc-clustering |
| 输入 | imzML + 算法配置 | imzML | 已完成的 Zarr |
| 特点 | 可选峰检测、归一化、对齐、降噪、基线校正 | 无算法，纯格式转换 | UMAP/KMeans，结果写回源 Zarr |
| 去重 | 无 | 同文件已有完成结果时直接复用 | 幂等，重复触发安全 |
| 产物 | 新 Zarr 目录 | 新 Zarr 目录 | 写回源 Zarr，不产生新目录 |

## 5. 实验与数据集合管理

`DataCollection`（数据集合）用于将多个文件组织在一起，支持：

- 创建集合、添加/移除成员
- 设置公开分享（生成 public_id）
- 按集合查看成员文件、成员数和总大小（集合详情当前不直接聚合 Run 结果）

Origin 对外以查询为主，由上传回调内部创建/更新，用户不直接操作 Origin。

## 6. 状态机和终态规则

每条 Run 有两个独立的状态字段：处理状态和聚类状态。

### 6.1 处理状态

| 状态 | 含义 | 能否被覆盖 |
|------|------|-----------|
| `PROCESSING` | 已触发 FC，等待回调 | — |
| `COMPLETED` | 结果路径和大小已校验落库 | 不被覆盖 |
| `FAILED` | FC 失败、回调异常或超时 | 可被迟到的成功回调翻转 |
| `DELETING` | 已登记删除，等待 Worker 清理 OSS | 删除收尾后记录消失 |
| `DELETE_FAILED` | OSS 清理失败 | 有权限的请求可重投删除 |

### 6.2 聚类状态

聚类复用 Run 记录，仅更新 `clustering_status` 字段，取值与处理状态相同（`None` 表示尚未聚类）。聚类的开始和超时单独判定。

### 6.3 关键规则

- Algorithm 失败回调只在 processing 状态落 failed；串行重复成功回调会跳过，但并发重复回调仍有重复计费窗口
- Clustering 回调当前没有终态保护，后到的成功/失败结果可覆盖先到结果
- 长时间没有回调的"僵尸"任务由定时巡检标记为 failed
- 被超时误判的 run 收到迟到的成功回调时可以翻转为 completed

## 7. Zarr 结果访问

`GET /processes/{run_id}/zarr` 返回结果目录和只读 STS 凭证：

- 仅限 `completed` 的 run
- 权限：所有者、管理员、或公开文件的直转 run
- 凭证有有效期并短期缓存
- 前端通过 OSS SDK 随机读取 Zarr 分块，用于渲染质谱图像

## 8. 权限、归属和配额

| 维度 | 规则 |
|------|------|
| 创建处理 | 文件所有者、管理员，或任意登录用户针对公开文件 |
| 查看结果 | 所有者、管理员、或公开文件的直转结果 |
| 删除 Run | 当前只允许 Run 创建者；删除接口没有管理员豁免 |
| 处理配额 | 按成功输出的累计大小计，成功回调时累加，删除时退还 |
| 上传配额 | 不因处理变化 |

## 9. 删除与结果清理

- 删除 Run：清理 OSS 上的 Zarr 结果目录，退还处理配额，删除记录
- 删除文件时：其全部运行记录和结果对象会一并清理（级联删除）
- 删除直转 Run：同时解除文件与默认直转结果的关联

## 10. 超时、失败和迟到回调

| 场景 | 处理方式 |
|------|---------|
| FC 执行超时 | 定时任务 `cleanup_stale_process_runs` 标记为 FAILED |
| FC 重试导致串行重复成功回调 | 读到 completed 后跳过；并发重复回调仍有重复计费窗口 |
| 超时误判后的迟到成功回调 | 可从 FAILED 翻转为 COMPLETED |
| FC 崩溃或消息丢失 | 由超时兜底任务判死 |

## 11. 代码入口索引

| 文件 | 职责 |
|------|------|
| `api/processing_api.py` | 处理路由（创建、查询、删除、Zarr 访问） |
| `api/callback_api.py` | 处理回调（algorithm_callback、clustering_callback） |
| `api_services/processing_service.py` | 处理业务逻辑 |
| `api_services/experiment_service.py` | Origin 管理 |
| `api_services/collection_service.py` | 数据集合管理 |
| `models/processing_models.py` | ProcessRun 等数据模型 |
| `models/experiment_models.py` | OriginImzML、DataCollection 等数据模型 |
