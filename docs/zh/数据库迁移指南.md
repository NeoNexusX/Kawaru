# 数据库迁移指南

本文定义 Kawaru 后端数据库结构变更的统一方案，覆盖 Alembic 接入、配置管理、开发流程、GitHub Actions 验证、dev/prod 部署、备份与失败处理。

## 1. 最终决策

- 使用 Alembic 作为唯一的数据库结构版本管理工具。
- 数据库驱动统一使用项目现有的 `mariadb+asyncmy`，不再引入同步 Engine 或 PyMySQL。
- 应用启动时不再调用 `SQLModel.metadata.create_all()`，也不在 FastAPI 进程中自动升级数据库。
- 数据库升级由同一镜像中的一次性 `migrate` 进程执行；升级成功后才启动 app、worker 和 beat。
- GitHub Actions 的第一个质量门禁是 `migration-check`：在一次性的临时 MariaDB 上验证全部迁移。
- Action 只执行和验证已经提交的迁移文件，绝不自动生成迁移并提交代码。
- 第一次只接入 Alembic 基线，不同时修改业务表；基线在 dev/prod 验证完成后，才开发 `UserFileLink.link_id` 和集合表。

总体流程如下：

```text
修改 SQLModel
    ↓
生成并人工审核 Alembic revision
    ↓
PR migration-check：临时 MariaDB 验证
    ↓
构建包含迁移文件的镜像
    ↓
CD 备份数据库并运行 migrate
    ↓
迁移成功后启动新版本服务
```

## 2. 为什么 CI 需要临时 MariaDB

“在临时 MariaDB 验证迁移”指的是：GitHub runner 为当前 PR 启动一套全新的 MariaDB 11.4，数据库中没有任何业务数据，也没有历史残留；迁移检查结束后，整个容器和数据都会被销毁，不影响 dev 或 prod。

CI 实际创建两个临时业务库：

- `kawaru_empty` 从 `base` 一次升级到 `head`，验证新环境可以完整重建，并检查整条历史链没有断裂。
- `kawaru_previous` 先升级到当前 head 的直接父 revision，再执行父 revision → head，专门验证本次增量升级路径。当前只有 baseline 时，父 revision 是 `base`，两项检查会部分重复；从第二个 revision 开始就会真正覆盖“上一版本升级”。

只测上一版本不够：新部署、测试环境和灾难恢复仍然需要从空库重建；只测空库也不够，因为生产发布走的是已有库增量升级。因此两个方向都保留。

它主要验证四类问题：

1. **全新安装**：一个空数据库能否从 Alembic `base` 顺序升级到最新 `head`。
2. **模型一致性**：升级后的真实表结构是否与当前 SQLModel 完全一致。
3. **历史升级**：旧 revision 中的数据能否被后续 revision 正确回填和约束。
4. **迁移图合法性**：是否只有一个 head，是否存在冲突、断链或遗漏的 migration。

临时数据库验证不是现有 API 端到端测试的替代品，而是现有测试流程最前面的数据库质量门禁。迁移检查失败时，不应继续构建镜像和运行集成测试。

## 3. 需要增加的文件

```text
Kawaru/
├── alembic.ini
├── migrations/
│   ├── env.py
│   ├── script.py.mako
│   └── versions/
├── database/
│   ├── migration.py
│   ├── migration_config.py
│   ├── model_registry.py
│   └── schema_guard.py
└── tests/
    └── migrations/
```

### 3.1 alembic.ini

只保存不敏感的静态设置：

```ini
[alembic]
script_location = %(here)s/migrations
prepend_sys_path = .
file_template = %%(year)d%%(month).2d%%(day).2d_%%(rev)s_%%(slug)s
```

`alembic.ini` 中不写数据库地址、用户名或密码，避免密钥进入 Git。

### 3.2 migrations/env.py

职责是：

- 按 `init_env()` → `init_logging()` → `init_config()` 的顺序完成最小初始化，但不调用会初始化 OSS、Celery 的完整 `bootstrap()`。
- 通过 `model_registry.py` 导入所有数据库模型。
- 设置 `target_metadata = SQLModel.metadata`。
- 创建一个短生命周期的 `asyncmy` Engine。
- 通过 `connection.run_sync()` 执行 Alembic 的同步迁移上下文。

核心结构：

```python
async def run_async_migrations() -> None:
    engine = create_async_engine(database_url, pool_pre_ping=True)
    try:
        async with engine.connect() as connection:
            await connection.run_sync(do_run_migrations)
    finally:
        await engine.dispose()
```

配置 Alembic 比较：

```python
context.configure(
    connection=connection,
    target_metadata=SQLModel.metadata,
    compare_type=True,
    compare_server_default=True,
)
```

迁移进程复用项目的数据库配置和 `asyncmy` 驱动，但不复用 FastAPI 进程内的全局 `_ASYNC_ENGINE`。

### 3.3 database/model_registry.py

集中导入全部数据库模型，避免某个模型没有被 import 而导致 Alembic 将对应表误判为需要删除。

```python
def import_all_models() -> None:
    import models.user_models
    import models.file_models
    import models.link_models
    import models.experiment_models
    import models.processing_models
```

这里先登记当前已经存在的表模型；以后新增 `models.collection_models` 等 `table=True` 模型时，必须在修改 SQLModel 的同一个 PR 中同步登记。

### 3.4 database/migration.py

提供统一命令：

```bash
python -m database.migration upgrade
python -m database.migration verify
python -m database.migration check-heads
```

`upgrade` 的职责：

1. 根据迁移 URL 连接 MariaDB 的 `mysql` 系统库并执行幂等的 `CREATE DATABASE IF NOT EXISTS`；Docker 环境通常已由 `MARIADB_DATABASE` 创建数据库，这一步主要服务本地和 CI 的独立临时库。
2. 连接目标数据库并通过 MariaDB `GET_LOCK()` 获取迁移锁。
3. 执行 `alembic upgrade head`。
4. 校验数据库当前 revision 与代码唯一 head 一致。
5. 释放迁移锁。

迁移锁用于防止 Action、人工部署或多台服务器同时升级同一个数据库。

### 3.5 database/schema_guard.py

FastAPI 启动时只检查数据库 revision，不执行迁移：

```text
数据库 current == 代码 head：允许启动
数据库 current != 代码 head：启动失败
```

worker 和 beat 通过 Compose 依赖 `migrate` 成功完成，不需要各自修改数据库。

## 4. 配置信息放在哪里

配置分为三类，不能全部堆在 `alembic.ini` 中。

### 4.1 项目数据库配置

继续使用现有 `{dev,prod}-config.yaml`：

```yaml
database:
  host: mariadb
  port: 3306
  db_name: kawaru
  db_type: mariadb
  db_username: root
```

数据库密码继续来自服务器 `.env`：

```text
DATABASE_PASSWORD=...
```

迁移环境根据这些配置使用 SQLAlchemy `URL.create()` 构造连接地址，避免密码中的 `@`、`:` 等字符破坏 URL：

```python
URL.create(
    drivername="mariadb+asyncmy",
    username=config.database.db_username,
    password=os.environ["DATABASE_PASSWORD"],
    host=config.database.host,
    port=config.database.port,
    database=config.database.db_name,
    query={"charset": "utf8mb4"},
)
```

### 4.2 CI 临时数据库配置

CI 继续加载仓库中的 `docker/test-config.yaml`，供模型读取字段长度等应用配置；数据库连接单独通过 Action 环境变量覆盖：

```text
MIGRATION_DATABASE_URL=mariadb+asyncmy://root:kawaru-test-pass@127.0.0.1:3306/kawaru?charset=utf8mb4
```

测试密码只属于一次性 CI 容器，可以明文写在 Workflow 中，不使用生产密码。

`MIGRATION_DATABASE_URL` 只作为迁移工具的显式覆盖项：设置时优先使用；未设置时回退到项目 YAML + `DATABASE_PASSWORD`。业务 API 不读取这个变量。

### 4.3 备份配置

备份属于部署配置，不属于应用业务配置。当前直接在 dev/prod CD Workflow 中固定为：

```text
dev:  ./data/backups，保留 7 天
prod: ./data/backups，保留 30 天
```

路径相对于服务器的 `/opt/kawaru-dev` 或 `/opt/kawaru-prod`，最终都会落到宿主机 `data/backups`。以后需要按服务器覆盖时，再改成 GitHub Environment variable 或专用部署配置；不要把备份目录写进 `alembic.ini`，也不要混入业务 YAML。

## 5. CI 的 migration-check 如何执行

当前 Workflow 只在代码 push 到 `test` 后运行，无法在 PR 合并前拦截错误，因此先补充触发条件：

```yaml
on:
  pull_request:
    branches: [test]
  push:
    branches: [test]
  workflow_dispatch:
```

然后在 `.github/workflows/ci.yml` 中增加第一个 job：

```yaml
jobs:
  migration-check:
    runs-on: ubuntu-latest
    services:
      mariadb:
        image: mariadb:11.4
        env:
          MARIADB_ROOT_PASSWORD: kawaru-test-pass
        ports:
          - 3306:3306
        options: >-
          --health-cmd="mariadb-admin ping -h 127.0.0.1 -uroot -pkawaru-test-pass"
          --health-interval=5s
          --health-timeout=5s
          --health-retries=20
    env:
      CONFIG_PATH: docker/test-config.yaml
      REGION_PATH: external/countries-states-cities-database/json/countries.json
      DATABASE_PASSWORD: kawaru-test-pass
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - uses: astral-sh/setup-uv@v7
      - run: uv sync --frozen
      - name: Require one Alembic head
        run: uv run python -m database.migration check-heads
      - name: Rebuild an empty database to head
        env:
          MIGRATION_DATABASE_URL: mariadb+asyncmy://root:kawaru-test-pass@127.0.0.1:3306/kawaru_empty?charset=utf8mb4
        run: |
          uv run python -m database.migration upgrade
          uv run python -m database.migration verify
          uv run alembic check
      - name: Upgrade the previous revision to head
        env:
          MIGRATION_DATABASE_URL: mariadb+asyncmy://root:kawaru-test-pass@127.0.0.1:3306/kawaru_previous?charset=utf8mb4
        run: uv run python -m database.migration test-upgrade-from-previous
      - name: Run migration data tests
        run: uv run pytest -c pytest.ini --confcutdir=tests/migrations tests/migrations -q

  static-checks:
    needs: migration-check
```

后续 `build-image` 继续依赖 `static-checks`。这样 migration-check 是 CI 流程中最先执行、失败即停止的步骤。

这里使用独立 job，而不是塞进现有 `integration-test`：MariaDB service 的生命周期只属于这个 job，而且迁移失败时无需等待镜像构建。GitHub Actions 的 job 默认可能并行，必须让 `static-checks` 显式 `needs: migration-check` 才能保证顺序。

`alembic check` 比较“已升级数据库”和“当前 SQLModel”，如果开发者修改了模型但忘记提交 revision，它会失败。

### 5.1 哪些验证不需要单独写 pytest

以下由通用 CI 命令自动覆盖：

- 空数据库能否升级到 head。
- 直接父 revision 能否升级到 head。
- migration 是否存在语法或 DDL 错误。
- 数据库 revision 是否到达 head。
- SQLModel 与实际表结构是否一致。
- 是否产生多个 Alembic head。

### 5.2 哪些变更必须写迁移测试

只要 migration 包含数据逻辑，就必须在 `tests/migrations/` 编写测试，例如：

- 为已有行回填非空字段。
- 根据旧字段计算新字段。
- 拆表、合表或迁移关联关系。
- 增加唯一约束前清理重复数据。
- `UserFileLink.link_id` 中“首次上传用户优先”的历史排序。

数据迁移测试采用：

```text
upgrade 到旧 revision
→ 插入旧结构数据
→ upgrade 到新 revision
→ 查询并断言新数据
```

普通的“新建空表”通常不需要专门写 pytest，空库升级和 `alembic check` 已经能够覆盖；但重要外键删除策略仍建议写集成测试。

## 6. 为什么要保存多个 migration 版本

保存 migration 历史是 Alembic 等迁移工具的标准用法。

版本文件组成一条有向迁移链：

```text
baseline → link_id → collections → 后续修改
```

它们的作用是：

- 让处于不同旧版本的 dev/prod 数据库都能升级到当前版本。
- 让新环境从空数据库完整重建。
- 记录每次结构和数据变更，方便审计与排查。
- 在测试中还原旧结构并验证升级逻辑。
- 必要时提供 downgrade 路径。

数据库中的 `alembic_version` 通常只保存当前 head，不会把每个历史版本都复制成数据库记录；完整历史保存在 Git 中的 migration 文件里。

早期讨论中的 `0001`、`0002`、`0003` 是为了说明顺序。实际项目建议使用 Alembic 自动生成的 revision ID，并在文件名中加入日期和描述，例如：

```text
20260824_a13f2c9b_baseline_current_schema.py
20260826_b91d6e42_add_user_file_link_sequence.py
20260830_c072a611_create_data_collections.py
```

这样多人并行开发时比手写连续数字更不容易冲突。

当 migration 数量非常多，并且所有受支持环境都已经升级到某个稳定版本后，可以专门安排一次“重新建立 baseline”的维护工作；不能日常随意删除已经部署过的 revision。

## 7. 第一次引入 Alembic 的执行方案

第一次接入必须与集合功能分开完成。

### 阶段 A：建立迁移基础设施

1. 在 `pyproject.toml` 增加 Alembic，并更新 `uv.lock`。
2. 增加 `alembic.ini`、异步 `migrations/env.py`、迁移命令和模型注册器。
3. 根据当前 SQLModel 创建 baseline revision。
4. 在临时空 MariaDB 执行 `upgrade head`，确认能建立完整现有结构。
5. 把 migration-check 加到 CI 最前面。
6. 此阶段不修改任何现有业务表和数据。

### 阶段 B：接管现有 dev 数据库

1. 备份 dev 数据库。
2. 在数据库副本上核对当前结构与 baseline。
3. 对现有 dev 数据库执行：

```bash
docker compose -f docker-compose.dev.yml -p kawaru-dev run --rm migrate \
  python -m database.migration stamp-baseline --confirm
docker compose -f docker-compose.dev.yml -p kawaru-dev run --rm migrate \
  python -m database.migration verify
```

命令会先比较现有数据库与当前 SQLModel；存在结构差异时拒绝 stamp。校验通过后，stamp 只写入 baseline revision，不执行 baseline 中的建表语句。

4. 部署 migrate 流程并观察至少一个发布周期。若在 stamp 前误触发新 CD，迁移进程会因为“非空且未版本化”而安全失败，旧服务不会被替换；完成 stamp 后重新运行 CD。

### 阶段 C：接管 prod 数据库

重复 dev 的备份、结构核对、stamp、check 和部署验证，只把 Compose 文件名和项目名替换为 prod。第一次 stamp 必须是受控操作，不能看到没有 `alembic_version` 就自动执行。

### 阶段 D：停止 create_all

确认 dev/prod 都已经由 Alembic 接管后：

- 数据库不存在时由 `database.migration upgrade` 创建，不再由 FastAPI 启动过程负责。
- 删除或停用 `create_db_and_tables()` 中的 `SQLModel.metadata.create_all()`。
- 从 FastAPI lifespan 中移除建表操作。
- 应用启动只执行 schema guard。

## 8. 后续修改 SQLModel 的开发流程

### 8.1 开始开发前

```bash
git checkout test
git pull origin test
git checkout -b feature/<topic>
uv sync --frozen
uv run python -m database.migration upgrade
```

确认本地数据库已经位于当前 head。

### 8.2 修改模型并生成 revision

先修改 SQLModel，然后执行：

```bash
uv run alembic revision --autogenerate -m "create data collections"
```

自动生成只是初稿，开发者必须检查：

- 表名和列名是否正确。
- 是否误删未导入的表。
- 字段类型、长度、默认值和 nullable 是否正确。
- 主键、唯一索引、普通索引是否完整。
- 外键的 `ON DELETE` 是否符合业务规则。
- upgrade 和 downgrade 是否安全。
- 是否需要历史数据回填。

Alembic 无法自动理解“谁是首次上传者”等业务含义，数据回填必须手写。

### 8.3 本地验证

```bash
uv run python -m database.migration upgrade
uv run python -m database.migration verify
uv run alembic check
uv run pytest -c pytest.ini --confcutdir=tests/migrations tests/migrations -q
```

然后运行与业务变更相关的 API 测试。

### 8.4 PR 必须包含

- SQLModel 修改。
- 新 Alembic revision。
- 必要的数据回填逻辑。
- 数据迁移测试。
- 接口和部署文档更新。

禁止：

- 直接在线上执行未入库的 `ALTER TABLE`。
- 修改已经部署到共享环境的旧 revision。
- 只修改 SQLModel 而不提交 migration。
- Action 自动生成 migration 并提交。
- 未解决多个 Alembic head 就合并 PR。

多人分支产生多个 head 时，应先同步 `test`，然后创建 Alembic merge revision，不能让 CD 猜测应该执行哪条分支。

## 9. Docker 与 CD 流程

dev、prod、test Compose 都增加一次性服务：

```yaml
migrate:
  image: ${APP_IMAGE:?}
  restart: "no"
  depends_on:
    mariadb:
      condition: service_healthy
  env_file: [.env]
  command: ["python", "-m", "database.migration", "upgrade"]
```

app、worker、beat 增加：

```yaml
depends_on:
  migrate:
    condition: service_completed_successfully
```

CD 执行顺序：

```text
pull 新镜像
→ 启动/确认 MariaDB 和 Redis 健康
→ 记录当前 revision 并备份
→ 使用 --force-recreate 前台运行 migrate，并检查退出码
→ 校验 revision
→ 启动新 app、worker、beat
→ readiness 检查
```

每次部署都必须重新创建一次 migrate 容器，不能因为上一次留下了成功退出的容器而跳过迁移。示意命令：

```bash
docker compose pull migrate app worker beat
docker compose up --no-deps --force-recreate \
  --abort-on-container-exit --exit-code-from migrate migrate
docker compose up -d --wait app worker beat
```

第二条命令非零退出时，Workflow 立即停止，不执行第三条。若 Compose 版本对已退出依赖的处理不稳定，可以改用 `docker compose run --rm migrate`，但此时 app、worker、beat 不再声明对 migrate 的自动依赖，必须完全依靠同一 CD 脚本保证先后顺序；两种模式只选一种，项目首选前者。

dev 和 prod 的 GitHub Actions 都应设置：

```yaml
concurrency:
  cancel-in-progress: false
```

避免新的 push 中断正在执行的数据库 DDL。数据库 `GET_LOCK()` 是第二层并发保护。

## 10. 数据库备份

迁移前执行逻辑备份：

```bash
mkdir -p "$DB_BACKUP_DIR"

docker compose exec -T mariadb sh -lc \
  'mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" \
   --single-transaction --routines --triggers kawaru' \
  | gzip > "$DB_BACKUP_DIR/$(date +%Y%m%d-%H%M%S)-${GITHUB_SHA}.sql.gz"
```

备份位于宿主机，不放在一次性应用容器中：

```text
/opt/kawaru-dev/data/backups/
/opt/kawaru-prod/data/backups/
```

第一阶段保存在服务器本地；生产环境后续应再同步到独立私有 OSS 或另一存储位置，防止数据库磁盘和本地备份同时损坏。数据库备份包含用户信息，必须限制权限，不能放到公开 Bucket。

## 11. 迁移失败与回滚

### 迁移失败

- 不启动新版本 app、worker、beat。
- 保留旧版本服务。
- 保存 migrate 日志、迁移前 revision 和目标 revision。
- 不在生产环境自动执行 downgrade。
- 根据实际情况修复 migration 后重试，或从备份恢复。

MariaDB DDL 不能假设全部可以事务回滚，自动 downgrade 可能扩大损坏范围。

### 迁移成功但新应用失败

应用镜像可以回滚到旧版本，但数据库通常保留新 schema。因此日常迁移必须优先采用向后兼容的增量修改。

删除列、重命名列等破坏性操作采用 expand-contract：

```text
先增加新结构
→ 部署兼容新旧结构的代码
→ 回填并切换读写
→ 确认旧代码不再使用
→ 后续独立 revision 删除旧结构
```

## 12. 当前集合功能的迁移顺序

Alembic 基线接管完成前，不提交集合表结构变更。

接管完成后按两个独立 revision 开发：

1. `add_user_file_link_sequence`
   - 为 `UserFileLink` 增加非主键自增 `link_id`。
   - 保留 `(user_id, file_id)` 联合主键。
   - 增加 `UNIQUE(link_id)` 和查询索引。
   - 新增关联以后按每个 `file_id` 的最小 `link_id` 判断首次上传用户，不使用用户名判断。
   - 数据库表没有可靠的“从上到下”顺序；现有链接不能仅凭迁移时新分配的 `link_id` 证明历史先后。迁移前先用旧 `first_uploaded_by` 辅助核对并输出用户名重复、用户不存在、文件无链接等异常，确认或修正后再按明确顺序重建链接；对应过程必须写数据迁移测试。
   - 验证完成后再单独移除冗余的 `FileInDB.first_uploaded_by`，不能在同一 revision 中直接删除回退依据。

2. `create_data_collections`
   - 创建 `data_collection`。
   - 创建 `collection_member`。
   - 配置联合主键、唯一约束、索引和外键删除策略。

两个 revision 在临时 MariaDB、dev 和 prod 顺序执行。数据库结构稳定后再发布集合后端接口，最后发布前端页面。

## 13. 完成标准

迁移体系满足以下条件后，才开始集合表开发：

- 空 MariaDB 可以从 base 升级到 head。
- 现有 dev/prod 数据库均已正确 stamp baseline。
- `alembic check` 无模型差异。
- CI 能阻止遗漏 migration 和多个 head。
- app 启动不再执行 `create_all()`。
- dev/prod 部署都先备份、再 migrate、最后启动应用。
- 迁移失败不会启动新版本服务。
- 已实际验证至少一次数据库备份恢复。
