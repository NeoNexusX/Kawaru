# 数据库迁移指南

本文定义 Kawaru 后端数据库结构变更的统一方案，覆盖 Alembic 接入、配置管理、开发流程、GitHub Actions 验证、dev/prod 部署、备份与失败处理。

```text
修改 SQLModel
    ↓
生成并人工审核 Alembic revision
    ↓
PR migration-check：临时 MariaDB 验证
    ↓
构建包含迁移文件的镜像
    ↓
CD 备份数据库并运行 migrate 升级
    ↓
迁移成功后启动新版本服务
```

---

## 1. 架构与文件组成

```text
Kawaru/
├── alembic.ini                 # Alembic 基础配置文件
├── migrations/
│   ├── env.py                  # 迁移运行时环境与异步驱动桥接
│   ├── script.py.mako          # 新迁移文件生成模板
│   └── versions/               # 历史迁移脚本版本链
├── database/
│   ├── migration.py            # 统一迁移 CLI（upgrade, verify, stamp 等）
│   ├── migration_config.py     # 迁移数据库连接串解析
│   ├── model_registry.py       # SQLModel 模型集中注册
│   └── schema_guard.py         # 应用启动时的版本校验哨兵
└── tests/
    └── migrations/             # 数据迁移测试目录
```

### 1.1 `alembic.ini`

只保存不敏感的静态设置：

```ini
[alembic]
script_location = %(here)s/migrations
prepend_sys_path = .
file_template = %%(year)d%%(month).2d%%(day).2d_%%(rev)s_%%(slug)s
```

`alembic.ini` 中不写入数据库地址、用户名或密码，避免密钥进入 Git。

### 1.2 `migrations/env.py`

核心职责：

- 按 `init_env()` → `init_logging()` → `init_config()` 顺序完成最小初始化，不调用会连接 OSS、Celery 的完整 `bootstrap()`。
- 通过 `model_registry.py` 导入所有数据库模型，确保 `SQLModel.metadata` 包含全量表结构。
- 设置 `target_metadata = SQLModel.metadata`。
- 创建短生命周期的 `asyncmy` Engine，通过 `connection.run_sync()` 执行 Alembic 的同步迁移上下文。
- 配置字段类型比对与服务端默认值比对（`compare_type=True`, `compare_server_default=True`）。

迁移进程复用项目的数据库配置和 `asyncmy` 驱动，但不复用 FastAPI 进程内的全局连接池。

### 1.3 `database/model_registry.py`

集中导入全部数据库模型，避免某个模型未被 import 而导致 Alembic 将对应表误判为“需删除（`remove_table`）”：

```python
def import_all_models() -> None:
    import models.user_models
    import models.file_models
    import models.link_models
    import models.experiment_models
    import models.processing_models
```

> **注意**：后续新增包含 `table=True` 的新模型文件时，必须在同一个 PR 中同步在 `model_registry.py` 中登记。

### 1.4 `database/migration.py`

提供项目统一的迁移 CLI 命令：

```bash
python -m database.migration check-heads                # 校验是否存在分叉 head
python -m database.migration upgrade                    # 升级数据库到最新 head
python -m database.migration verify                     # 校验数据库当前版本是否与代码 head 一致
python -m database.migration stamp-baseline --confirm   # 对结构一致的存量库打上基线版本标记
python -m database.migration test-upgrade-from-previous # 测试从上一版本升级到 head
```

- `upgrade` 执行时会首先连接 MariaDB 并通过 `GET_LOCK()` 获取命名锁，防止多实例部署时并发执行迁移导致冲突。

### 1.5 `database/schema_guard.py`

FastAPI 应用启动时的版本守卫：

```text
数据库 current == 代码 head：允许启动
数据库 current != 代码 head：启动失败抛出异常
```

应用启动时**只校验版本，不主动执行 DDL 迁移**，数据库结构变更必须由独立的 `migrate` 容器先期完成。

## 2. 配置管理规范

配置分为三类，职责明确分离：

### 2.1 项目数据库配置
继续使用现有的 `{dev,prod}-config.yaml` 搭配服务器 `.env` 中的 `DATABASE_PASSWORD`。迁移工具通过 SQLAlchemy `URL.create()` 构造安全的数据库连接串，避免密码中特殊字符破坏 URL。

### 2.2 CI 临时数据库配置
CI 运行测试时加载仓库中的 `docker/test-config.yaml`，并通过 Action 环境变量显式指定连接：
```text
MIGRATION_DATABASE_URL=mariadb+asyncmy://root:kawaru-test-pass@127.0.0.1:3306/kawaru?charset=utf8mb4
```
`MIGRATION_DATABASE_URL` 仅供迁移命令行工具作为覆盖项读取，业务 API 不读取此变量。

### 2.3 备份配置
备份属于部署运维配置，不写进业务 YAML 或 `alembic.ini`。CD 工作流中统一保存在宿主机目录：
- **dev**：`./data/backups`，保留 7 天
- **prod**：`./data/backups`，保留 30 天

## 3. CI 的 migration-check 自动化验证

在 `.github/workflows/ci.yml` 中配置独立的 `migration-check` job，前置于镜像构建与静态检查：

```yaml
jobs:
  migration-check:
    runs-on: ubuntu-latest
    services:
      mariadb:
        image: mariadb:11.4
        env:
          MARIADB_ROOT_PASSWORD: kawaru-test-pass
        ports:
          - 3306:3306
        options: >-
          --health-cmd="mariadb-admin ping -h 127.0.0.1 -uroot -pkawaru-test-pass"
          --health-interval=5s
          --health-timeout=5s
          --health-retries=20
    env:
      CONFIG_PATH: docker/test-config.yaml
      REGION_PATH: external/countries-states-cities-database/json/countries.json
      DATABASE_PASSWORD: kawaru-test-pass
    steps:
      - uses: actions/checkout@v6
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - uses: astral-sh/setup-uv@v7
      - run: uv sync --frozen
      - name: Require one Alembic head
        run: uv run python -m database.migration check-heads
      - name: Rebuild an empty database to head
        env:
          MIGRATION_DATABASE_URL: mariadb+asyncmy://root:kawaru-test-pass@127.0.0.1:3306/kawaru_empty?charset=utf8mb4
        run: |
          uv run python -m database.migration upgrade
          uv run python -m database.migration verify
          uv run alembic check
      - name: Upgrade the previous revision to head
        env:
          MIGRATION_DATABASE_URL: mariadb+asyncmy://root:kawaru-test-pass@127.0.0.1:3306/kawaru_previous?charset=utf8mb4
        run: uv run python -m database.migration test-upgrade-from-previous
      - name: Run migration data tests
        run: uv run pytest -c pytest.ini --confcutdir=tests/migrations tests/migrations -q

  static-checks:
    needs: migration-check
```

### 3.1 哪些验证由 CI 通用命令自动覆盖
- 空数据库能否从零顺利升级到 `head`。
- 上一版本（parent revision）能否平滑升级到 `head`。
- migration 脚本中是否存在语法或 SQL DDL 错误。
- 数据库最终 revision 是否与代码预期 head 完全对齐。
- 当前 `SQLModel` 模型与升级后的实际表结构是否存在未同步差异（`alembic check`）。
- Git 历史中是否存在多头分叉（multiple heads）。

### 3.2 哪些变更必须编写数据迁移测试 (`tests/migrations/`)
只要 migration 包含**数据变更逻辑**，必须在 `tests/migrations/` 中编写专用测试：
- 为已有数据行回填非空字段。
- 根据旧字段计算/转换新字段格式。
- 拆表、合表或关系迁移。
- 增加唯一约束前的历史重复数据清洗。

**测试标准流程**：
```text
upgrade 到旧 revision → 插入旧结构样例数据 → upgrade 到新 revision → 查询并断言新数据正确性
```

## 4. 迁移历史与版本链管理

每次表结构变更生成独立的 revision 文件，串联成一条单向演进链：

```text
baseline (35048e902958) → add_feature_a → modify_table_b → ... → head
```

- **命名规范**：使用系统自动生成的日期前缀与唯一 ID，例如 `20260825_35048e902958_baseline_current_schema.py`。
- **不可变性**：一旦某个 revision 被合并到主分支并部署到 dev/prod 环境，**严禁修改或删除该历史文件**。
- **合并冲突处理**：多人并行开发产生多个 head 时，需使用 `alembic merge heads -m "merge branch a and b"` 创建显式 merge revision，禁止未解决分叉就提交 PR。

## 5. 首次接入 Alembic 的基线初始化方案【生产服操作】

当生产数据库已有存量数据，但尚未由 Alembic 管理时，必须执行**基线标记（Baseline Stamp）**。

### 5.1 步骤说明
1. **确认备份正常**：
   在合并 PR 触发首次部署前，先确认生产服务器已有备份且压缩包正常：
   ```bash
   cd /opt/kawaru-prod
   export APP_IMAGE=ghcr.io/neonexusx/kawaru:sha-<完整main提交SHA>
   SHA 详见：https://github.com/NeoNexusX/Kawaru/pkgs/container/kawaru
   # 查看最新备份
   ls -lh ./data/backups | tail
   
   # 校验备份压缩包完整性
   gzip -t ./data/backups/<最新备份文件>.sql.gz
   ```
   
2. **执行基线标记（Baseline Stamp）**：
   ```bash
   cd /opt/kawaru-prod
   
   docker compose -f docker-compose.prod.yml -p kawaru-prod run --rm migrate \
     python -m database.migration stamp-baseline --confirm
   ```

3. **异常处理（Schema 不一致拦截）**：
   `stamp-baseline` 会自动比对当前物理数据库与 Python 代码中的 `SQLModel` 模型。
   - **如果报错 `RuntimeError: Existing database does not match SQLModel metadata; baseline stamp refused:`**
     表明存量数据库中残留了代码已废弃的表（如旧版 `partindb`）、残留索引或字段注释不一致。
   - **解决方法**：确认无用后在数据库中清理对应残留表（如 `DROP TABLE IF EXISTS partindb;`）或对齐注释，然后重新执行 `stamp-baseline`。
   - 校验通过后，stamp 会在 `alembic_version` 表中写入基线版本号，且**不会重复执行任何建表 DDL**。

4. **完成校验并重新触发部署**：
   ```bash
   docker compose -f docker-compose.prod.yml -p kawaru-prod run --rm migrate \
     python -m database.migration verify
   
   docker compose -f docker-compose.prod.yml -p kawaru-prod run --rm migrate \
     alembic check
   ```
   校验通过后，在 GitHub Actions 中重新运行之前失败的 Prod CD 工作流即可。

## 6. 后续修改 SQLModel 的日常开发流程

### 6.1 开始开发前
同步最新代码，确认本地数据库位于最新 head：
```bash
git checkout test
git pull origin test
git checkout -b feature/<topic>
uv sync --frozen
uv run python -m database.migration upgrade
```

### 6.2 修改模型并生成 revision
修改 `models/*.py` 中的 SQLModel 定义后，执行自动生成命令：
```bash
uv run alembic revision --autogenerate -m "<变更描述>"
```

> [!IMPORTANT]
> **自动生成仅为初稿，开发者必须逐行审核生成的迁移文件**：
> 1. **确认表名与列名**：Alembic 无法识别“重命名列”，会误判为 `drop_column` + `add_column`，需手动修正为 `alter_column(..., new_column_name=...)`。
> 2. **约束与默认值**：检查 `nullable`、`server_default`、外键 `ondelete` 策略是否符合设计。
> 3. **评估是否需要数据回填**：如果新增非空字段或重构状态值，必须在 `upgrade()` 中手动编写数据迁移或回填 SQL。

### 6.3 本地全套测试与验证
提交前在本地运行完整验证集：
```bash
uv run python -m database.migration upgrade
uv run python -m database.migration verify
uv run alembic check
uv run pytest -c pytest.ini --confcutdir=tests/migrations tests/migrations -q
```
并运行与变更相关的 API 单元测试与集成测试。

### 6.4 PR 交付标准与合规红线
- **PR 必须包含**：SQLModel 变更、新 Alembic revision 脚本、必要的数据回填逻辑、迁移测试（如涉及数据变更）。
- **合规红线（严禁行为）**：
  - ❌ 禁止在线上数据库直接执行未经 Git 审核的 `ALTER TABLE`。
  - ❌ 禁止修改已推送到远程并在共享环境中生效的旧 revision 文件。
  - ❌ 禁止修改了 SQLModel 却漏提 migration 脚本。
  - ❌ 禁止存在多个未合并的 Alembic heads 时合并 PR。

## 7. 数据库备份策略

每次 CD 执行迁移升级前，CD 工作流会自动调用容器执行一致性逻辑备份：

```bash
mkdir -p "$DB_BACKUP_DIR"

docker compose exec -T mariadb sh -lc \
  'mariadb-dump -uroot -p"$MARIADB_ROOT_PASSWORD" \
   --single-transaction --routines --triggers kawaru' \
  | gzip > "$DB_BACKUP_DIR/$(date +%Y%m%d-%H%M%S)-${GITHUB_SHA}.sql.gz"
```

- 备份文件统一持久化在宿主机目录：
  - 开发服：`/opt/kawaru-dev/data/backups/`
  - 生产服：`/opt/kawaru-prod/data/backups/`
- 生产环境后续将进一步配置定时归档同步至独立私有 OSS，防止主机单点故障。

## 8. 迁移失败与回滚策略

### 8.1 迁移升级失败（Migrate 容器退出码非 0）
- CD 流程立即中断，**不启动新版本 `app`、`worker`、`beat`**，旧版本服务继续维持运行。
- 输出迁移错误日志，记录失败前 revision 与目标 revision。
- **禁止在生产环境自动执行 `downgrade`**（MariaDB 部分 DDL 为非事务性，自动 downgrade 可能导致二次损坏）。
- 开发者根据日志修复 migration 问题后重新发布，或由管理员从备份快照中恢复。

### 8.2 迁移成功但新应用逻辑异常
- 应用容器可以无缝回退到上一镜像版本，但数据库通常保留已升级的 schema。
- **设计原则**：日常数据库迁移必须遵循 **Expand-Contract（向前兼容演进）**：
  ```text
  1. Expand: 新增字段或表（允许为空或具备默认值，保持新老代码兼容）
  2. Migrate & Backfill: 部署新版本代码，完成数据回填与读写切换
  3. Contract: 确认旧逻辑彻底停用后，在后续独立版本中清理废弃字段
  ```
