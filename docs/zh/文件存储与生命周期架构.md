# 文件存储与生命周期架构

本文档介绍 Kawaru 文件业务的完整生命周期，包括上传下载、OSS 存储分层、文件状态流转和删除流程。配套架构图见下方链接。

## 1. 文件业务边界与核心对象

Kawaru 的文件内容不经过后端服务器，由客户端直连 OSS 上传下载。后端只负责校验、签名和状态管理。核心数据对象：

| 对象 | 说明 | OSS 路径示例 |
|------|------|-------------|
| 上传 ZIP | 用户上传的原始压缩包 | `data/{hash}/{file_id}.zip` |
| Origin 文件 | FC 解包后的 imzML + ibd | `origin/{hash}/{file_id}/{文件名}.imzML` |
| 处理结果 | 算法处理生成的 Zarr | `processed/run_{run_id}.zarr/` |
| 预览图 | TIC/UMAP 预览图 | `images/{file_id%1000:03d}/file_{file_id}/preview.jpg` |
| 打包 ZIP | 下载时 FC 重新打包的 ZIP | `packup/{file_id}.zip` |

## 2. 上传与下载全景

> [打开交互式架构图：文件上传下载流程](../frameworkmap/kawaru-file-flow.html)

### 2.1 上传流程

```
用户选择文件 → 前端计算哈希 → 调用预检 API
    ↓
预检返回 public_id（或秒传结果）
    ↓
前端用 public_id 获取 STS 临时凭证
    ↓
前端凭 STS 直传 ZIP 到 OSS
    ↓
OSS 事件触发解包 FC
    ↓
FC 解压 ZIP，写入 imzML + ibd 到 OSS
    ↓
FC 回调 API，校验通过后标记文件为 completed
```

关键规则：

- 预检和上传是两步操作：预检只返回 public_id，不签发 STS；前端再以 public_id（表单字段 `pre_public_id`）调上传接口获取 STS
- 如果其他用户已上传过相同文件（哈希匹配），预检直接返回秒传（`is_reuse=true`），前端不再调上传接口
- STS 凭证只对单个 OSS 对象有效，路径由后端指定，前端不能自行拼接
- OSS 直传成功不等于业务上传成功，客户端应以数据库状态 `completed` 为准

### 2.2 下载流程

系统有两套下载路径并存：

| 方式 | 接口 | 特点 |
|------|------|------|
| RAW 直链 | `GET /files/{public_id}/download_raw` | 为 imzML + ibd 各签一个预签名 URL，毫秒级响应，无中间产物 |
| ZIP 打包 | `GET /files/{public_id}/download` | FC 重新打包成单个 ZIP 再签名，首次可能返回 `<PACKING>` 需重试 |
| 免登录直链 | `GET /files/{public_id}/download_raw_noauth` | 无登录态、不限次数，用于公开文件分享 |

RAW 直链流程：API 校验权限和配额 → 检查 Origin 就绪 → 签发预签名 URL → 缓存 URL → 客户端直连 OSS 下载

ZIP 打包流程：API 检查是否有可用 ZIP → 有则签名返回 → 没有则触发 FC 打包 → 返回 `<PACKING>` → FC 完成后回调写 Redis → 客户端重试获取签名 URL

关键规则：

- `<PACKING>` 是占位响应，前端应间隔重试，并发请求不会触发重复打包
- 返回 `<PACKING>` 时不消耗下载次数，成功拿到 URL 才计一次
- 打包 ZIP 是临时对象，超过保留期没有被再次下载的会被清理

## 3. OSS 存储分层

> [打开交互式架构图：OSS 存储架构](../frameworkmap/kawaru-oss-storage.html)

### 3.1 访问方式

| 角色 | 访问 OSS 的方式 | 用途 |
|------|----------------|------|
| 客户端 | STS 临时凭证 / 预签名 URL | 直传上传、直连下载 |
| API 服务 | OssStorage 封装层 → Celery 任务 → Worker 调用 OSS SDK | 删除、标签、检查、签名 |
| FC 函数 | FC 内部访问 OSS | 解包写入、处理结果写入 |

API 不直接调用 OSS SDK，而是通过 `OssStorage` 封装层投递 Celery 任务，由 Worker 异步执行。这样避免 OSS 操作阻塞 API 请求。

### 3.2 对象路径规范

所有对象路径的根目录可在配置文件中调整：

| 内容 | 路径格式 |
|------|---------|
| 上传 ZIP | `{oss_zip_storage_root}/{file_verify_code}/{file_id}.zip` |
| Origin 文件 | `{oss_origin_storage_root}/{file_verify_code}/{file_id}/{原始文件名}` |
| 处理结果 | `{oss_processed_storage_root}/run_{run_id}.zarr/` |
| 预览图 | `images/{file_id%1000:03d}/file_{file_id}/`（目录，文件名按 `preview.jpg` 等约定） |
| 打包 ZIP | `{oss_packup_zip_storage_root}/{file_id}.zip` |

对象键第一段使用内容哈希或取模分片而非自增 `file_id`：OSS 按键名字典序分区，顺序递增的前缀会让并发写入集中到单一分区形成热点。存量对象沿用旧布局，读取与删除一律以 DB 落库的路径为准。

### 3.3 对象标签与生命周期

上传成功的核心文件（ZIP、imzML、ibd）会被标记为 `persistent`（持久保留），不受 OSS 生命周期规则影响。未被打标的遗留对象（上传失败的残留、过期的临时文件）由 OSS 生命周期规则自动回收。

### 3.4 对外标识与 OSS 路径中的 file_id（待办）

对外接口（文件元数据/下载/删除/公开/修改、算法处理、Origin 查询、集合成员）一律用 16 位 base62 随机串 `public_id` 标识文件，不返回内部自增 `file_id`，防止被枚举。

但 OSS 对象键中仍保留 `file_id`（zip 文件名、预览图目录名），因此以下两处对前端仍可见 `file_id`，属于有意保留：

- 上传接口返回的 `oss_path`（`data/{file_verify_code}/{file_id}.zip`）：前端必须按该路径直传，解包 FC 从文件名解析 `file_id` 后回调后端
- 文件响应中的 `image_path`（`images/{file_id%1000:03d}/file_{file_id}/`）：前端据此拼接预览图地址

**待办（暂不修改）**：若要彻底不暴露 `file_id`，需把对象键改为使用 `public_id`，涉及范围：

- 解包 FC：改为从对象键解析 `public_id`，并以 `public_id` 回调 `/callback/oss_upload_callback`（后端回调改为按 `public_id` 定位记录）
- 后端路径生成：上传路径（`OssStorage.prepare_storage_path`）、预览图目录（`background/processing_background.py` 的 `image_dest`）、打包 ZIP 路径及其回调反解（`packup_zip_path` / `parse_packup_zip_file_id`）
- 删除快照中按约定推导的路径（`composite_service` 的预览图目录等）
- TIC/UMAP 等图像回调参数（当前同样携带 `file_id`）
- 存量 OSS 对象：迁移到新路径，或过渡期内同时兼容新旧两种路径格式

## 4. 文件生命周期

> [打开交互式架构图：文件生命周期](../frameworkmap/kawaru-file-lifecycle.html)

### 4.1 状态定义

| 状态 | 含义 | 何时进入 |
|------|------|---------|
| 预检态（内部值为空字符串） | 已预占配额，尚未成功签发 STS | 预检创建记录时 |
| `UPLOADING` | 上传中 | 上传接口成功签发 STS 时 |
| `COMPLETED` | 完成 | FC 解包回调校验通过后 |
| `FAILED` | 失败 | 解包、校验或回调失败 |
| `DELETING` | 删除中 | 删除请求锁定文件行时 |
| `DELETE_FAILED` | 删除失败 | OSS 对象删除部分失败时 |

### 4.2 状态流转

```
预检创建（空状态） → 成功签发 STS → UPLOADING → FC 解包成功 → COMPLETED
          ↓                                  ↓
      空路径且过期清理                  解包失败 → FAILED → 过期清理

COMPLETED → 删除请求 → DELETING → OSS 全删 → 删除记录
                        ↓
                    部分失败 → DELETE_FAILED → 等待重试
```

## 5. 删除状态机

> [打开交互式架构图：文件删除流程](../frameworkmap/kawaru-delete-flow.html)

文件删除分两步完成，先登记后清理：

### 5.1 第一步：登记（同步，同一个请求内完成）

```
删除请求 → 鉴权（JWT + 文件归属/管理员）
    ↓
锁定文件行（SELECT ... FOR UPDATE）
    ↓
解绑当前用户与文件的关联
    ↓
如果还有其他持有者 → 仅退上传配额，返回 unlinked
    ↓
如果没有其他持有者 → 收集快照（OSS 路径列表），标记 DELETING
    ↓
提交事务
```

### 5.2 第二步：清理（异步，Celery 任务）

```
投递 delete_objects_task
    ↓
Worker 清理 Redis 缓存（packup 状态）
    ↓
按快照逐对象/目录删除 OSS
    ↓
全部成功 → 退处理配额 → 删除文件记录（级联删 Origin/Run）
    ↓
部分失败 → 标记 DELETE_FAILED → 等待重试
```

关键规则：

- 两次事务，两类配额：登记事务退上传配额（file_count / total_file_size），收尾事务退处理配额（processed_file_size）
- 快照覆盖范围：主文件、Origin 的 imzML/ibd、所有 Run 输出、预览图目录、打包 ZIP
- 不存在的对象视为删除成功（幂等）
- 删除失败保留 DB 行和处理配额，等待有权限的请求重投（通常需管理员）
- 共享文件解绑时只退当前用户的上传配额，不删除文件

## 6. 配额占用与退还

| 配额 | 占用时机 | 退还时机 |
|------|---------|---------|
| 文件数 | 预检建立关联时 +1 | 删除/解绑/过期清理时 -1 |
| 上传总大小 | 预检时按声明大小预占 | 删除/过期清理时退还 |
| 处理总量 | 处理成功回调时按输出大小累加 | 删除 Run 时退还 |
| 下载次数 | 成功获得下载 URL 时 +1 | 不退还 |

## 7. 一致性、幂等与补偿策略

| 场景 | 处理方式 |
|------|---------|
| OSS 直传成功但 FC 回调丢失 | 定时任务清理过期的 UPLOADING 记录 |
| FC 回调重复到达 | 幂等处理，不重复创建 Origin |
| 删除投递失败 | DELETING 状态保留，等待重试 |
| 删除部分成功 | DELETE_FAILED 状态保留，等待重投 |
| 并发删除同一文件 | 行锁保证只有一个请求进入删除流程，其余重取快照 |

## 8. 常见异常场景

| 场景 | 表现 | 处理方式 |
|------|------|---------|
| 上传 ZIP 格式错误 | FC 解包失败 | 文件标记 FAILED，过期后清理 |
| FC 回调超时 | 文件长时间 UPLOADING | 定时任务直接删除过期记录并退还配额，不先标记 FAILED |
| 打包 ZIP 过期被清理 | 下载时返回 `<PACKING>` | FC 重新打包 |
| Origin 对象被误删 | 下载 404 | 需人工介入 |
| 配额退还出现负数 | 退还后配额为负 | GREATEST 保护，不会出现负值 |
