# 部署指南（dev / prod）

push 到 `dev` / `main` 分支后，[.github/workflows/dev-cd.yml](../../.github/workflows/dev-cd.yml) / [.github/workflows/prod-cd.yml](../../.github/workflows/prod-cd.yml) 自动：
**构建镜像 → 推 GHCR → SSH 到对应服务器同步 compose → `pull && up -d --wait`**。

两个 CD **只做构建与部署**，不生成/修改任何密钥或配置。`.env` 与 `{dev,prod}-config.yaml` 由人一次性准备在服务器上，之后归你维护。

> **dev 与 prod 互不影响**：dev 跟 `dev` 分支、镜像 `dev-latest`、服务器 `/opt/kawaru-dev`、项目名 `kawaru-dev`；prod 跟 `main` 分支、镜像 `latest`、**独立的另一台 prod 服务器** `/opt/kawaru-prod`、项目名 `kawaru-prod`。两套互不影响。详见文末对照表。

---

## 1. 架构（Celery 分离模式）

### Dev

```
mariadb(13306)  ─┐
redis(16379)   ──┼─ app(8000)
                 ├─ worker (celery -Q default)
                 └─ beat   (celery 调度)
```

- `enable_embedded_celery: false`，app 不再 fork worker/beat；worker、beat 各自独立容器。
- 端口：app `8000`；mariadb 暴露 `13306`、redis 暴露 `16379`（非默认，便于外部检测）。
- 可以使用 panel 来查看对应的容器情况：
  <https://testpanel.neonexus.top/containers/container>

  ![dev-container-panel](https://neonexus-picture.oss-ap-southeast-1.aliyuncs.com/test/image-20260625111959965.png)

### Prod

```
mariadb(127.0.0.1:13306) ─┐
redis(127.0.0.1:16379)  ──┼─ app(8000)
                          ├─ worker (celery -Q default)
                          └─ beat   (celery 调度)
```

- `enable_embedded_celery: false`，app 不再 fork worker/beat；worker、beat 各自独立容器。
- 端口：app `8000`；**mariadb / redis 只绑回环 `127.0.0.1`**（正式环境不对公网开放，这是与 dev 的关键区别）。
- 如需从外部检测 DB/Redis，走 SSH 隧道，不要直接放开端口。

## 2. 服务器一次性准备

dev / prod 命令结构完全相同，只有目录名、配置名不同。两台机器各跑一遍。

### Dev — `/opt/kawaru-dev`

```bash
# 1) 目录
sudo mkdir -p /opt/kawaru-dev/data/{mariadb,redis,app,logs/{app,worker,beat}}
cd /opt/kawaru-dev

# 1.5) 顶层目录交给 SSH 登录用户（$USER = secrets.DEV_SSH_USER）
#      原因：dev-cd 用该用户 scp docker-compose.dev.yml 进这个目录，
#      若顶层是 root:root，drone-scp 会在 tar 步骤报 Permission denied。
sudo chown -R "$USER":"$USER" /opt/kawaru-dev

# 2) app/worker/beat 以 appuser(默认 uid 1000) 运行，给可写目录授权
#    确认 uid：docker run --rm ghcr.io/<owner>/kawaru:dev-latest id appuser
sudo chown -R 1000:1000 /opt/kawaru-dev/data/app /opt/kawaru-dev/data/logs

# 3) 放配置文件（从仓库复制模板，改成真实值）
# .env
# 		env 里面要有CONFIG_PATH=/app/config/dev-config.yaml
# 还有 config名字为dev-config.yaml
# 这俩都在/opt/kawaru-dev下，
完整效果如下：
[admin@iZbp11b9u15fgnmcy9l6teZ kawaru-dev]$ ls -alh
total 28K
drwxr-xr-x  3 admin admin 4.0K Jun 25 17:03 .
drwxr-xr-x. 5 root  root  4.0K Jun 25 00:31 ..
drwxr-xr-x  6 admin admin 4.0K Jun 25 00:31 data
-rw-r--r--  1 admin admin 4.5K Jun 25 00:41 dev-config.yaml
-rw-r--r--  1 admin admin 4.0K Jun 25 17:03 docker-compose.dev.yml
-rw-r--r--  1 admin admin 1.3K Jun 25 09:57 .env
```

### Prod — `/opt/kawaru-prod`

```bash
# 1) 目录
sudo mkdir -p /opt/kawaru-prod/data/{mariadb,redis,app,logs/{app,worker,beat}}
cd /opt/kawaru-prod

# 1.5) 顶层目录交给 SSH 登录用户（$USER = secrets.PROD_SSH_USER）
#      原因：prod-cd 用该用户 scp docker-compose.prod.yml 进这个目录，
#      若顶层是 root:root，drone-scp 会在 tar 步骤报 Permission denied。
sudo chown -R "$USER":"$USER" /opt/kawaru-prod

# 2) app/worker/beat 以 appuser(默认 uid 1000) 运行，给可写目录授权
#    确认 uid：docker run --rm ghcr.io/<owner>/kawaru:latest id appuser
sudo chown -R 1000:1000 /opt/kawaru-prod/data/app /opt/kawaru-prod/data/logs

# 3) 放配置（从仓库复制模板，改成真实值）
#    .env             → /opt/kawaru-prod/.env
# 	 env 里面要有CONFIG_PATH=/app/config/prod-config.yaml
#    prod-config.yaml → /opt/kawaru-prod/prod-config.yaml（文件名/路径不能变）
完整：效果如下：
[kawaru-prod]$ ls -alh
drwxr-xr-x  3 admin admin 4.0K Jun 25 17:14 .
drwxr-xr-x. 5 root  root  4.0K Jun 25 15:04 ..
drwxr-xr-x  6 admin admin 4.0K Jun 25 14:59 data
-rw-r--r--  1 admin admin 4.4K Jun 25 17:14 docker-compose.prod.yml
-rw-r--r--  1 admin admin 1.3K Jun 25 15:00 .env
-rw-r--r--  1 admin admin 4.6K Jun 25 15:03 prod-config.yaml
```

之后每次 push `dev` / `main` 自动滚动升级，数据不丢。

## 3. 落盘清单（bind mount → 本地）

以下数据都存储到宿主机器硬盘上，不在容器里面。dev / prod 布局一致。

| 内容 | 容器内 | 宿主机 |
|---|---|---|
| MariaDB | `/var/lib/mysql` | `data/mariadb` |
| Redis(AOF) | `/data` | `data/redis` |
| 本地存储 `local/ temp_chunks/ origin/ processed/` | `/app/data` | `data/app` |
| app 日志 | `/app/kawaru_logs` | `data/logs/app` |
| worker 日志 | `/app/kawaru_logs` | `data/logs/worker` |
| beat 日志 | `/app/kawaru_logs` | `data/logs/beat` |

> 日志按服务拆分到不同目录：避免 app/worker/beat 三个进程同时写同名文件导致 `RotatingFileHandler` 轮转冲突。

## 4. 常用运维

Dev触发任务前请开代理，触发后请关，prod不需要：

```bash
clashon
clashtun on
# ... 做事 ...
clashtun off
clashoff
关闭完成后请到：
[/opt/kawaru-dev]$ docker compose -f docker-compose.dev.yml down
[/opt/kawaru-dev]$ docker compose -f docker-compose.dev.yml up -d
然后看下日志能否正常启动，无法正常启动，重启服务器
参见：https://github.com/nelvko/clash-for-linux-install
```

其余操作对 dev / prod 几乎一致，只有少数地方随环境切换：

| 项 | Dev | Prod |
|---|---|---|
| 服务器目录 | `/opt/kawaru-dev` | `/opt/kawaru-prod` |
| compose 文件 | `docker-compose.dev.yml` | `docker-compose.prod.yml` |
| compose project | `kawaru-dev` | `kawaru-prod` |
| 镜像 tag | `ghcr.io/neonexusx/kawaru:dev-latest` | `ghcr.io/neonexusx/kawaru:latest` |
| 配置 yaml | `dev-config.yaml` | `prod-config.yaml` |
| DB / Redis 外部访问 | 直接连服务器 IP（端口 `13306` / `16379`） | 只绑回环，需先 SSH 隧道 |

```bash
# 1) 切到对应服务器目录
cd /opt/kawaru-dev    # dev
cd /opt/kawaru-prod   # prod

# 2) 查看配置 / 密码
cat .env

# 3) 查看管理员密码（仅 prod 启动过才有；首次启动会在 app 日志里打
#    "create admin user <name>, password <8位数字>"，重启不会重打）
sudo grep -rE "create admin user|user already exists" /opt/kawaru-prod/data/logs/app/

# 4) 看日志（按服务拆分；想看 app / beat / mariadb / redis，把末尾 service 名换掉即可）
#    注意：compose 文件里 image 引用了 ${APP_IMAGE} 变量（不在 .env 里），
#    直接跑 compose 命令会报 "required variable APP_IMAGE is missing a value"，
#    需先在当前 shell 导出该变量
export APP_IMAGE=ghcr.io/neonexusx/kawaru:dev-latest   # dev
export APP_IMAGE=ghcr.io/neonexusx/kawaru:latest       # prod
docker compose -f docker-compose.dev.yml  -p kawaru-dev  logs -f worker   # dev
docker compose -f docker-compose.prod.yml -p kawaru-prod logs -f worker   # prod

# 5) 改了 .env / config.yaml 后手动生效（配置 yaml 是 :ro 挂载，需要重建容器）
docker compose -f docker-compose.dev.yml  -p kawaru-dev  up -d   # dev
docker compose -f docker-compose.prod.yml -p kawaru-prod up -d   # prod

# 6) 外部检测 DB / Redis
#    dev：直接连服务器 IP
mysql  -h <服务器IP> -P 13306 -uroot -p
redis-cli -h <服务器IP> -p 16379 -a <REDIS_PASSWORD> ping
#    prod：先开 SSH 隧道再连本地端口
# ssh -L 13306:127.0.0.1:13306 -L 16379:127.0.0.1:16379 <PROD_SSH_USER>@<服务器IP>
mysql  -h 127.0.0.1 -P 13306 -uroot -p
redis-cli -h 127.0.0.1 -p 16379 -a <REDIS_PASSWORD> ping
# 数据库密码 / Redis 密码都在 .env 里

# 7) 确认 worker 已连上 broker（一次性，勿放进 healthcheck）
docker compose -f docker-compose.dev.yml  -p kawaru-dev  exec -T worker \
  celery -A celery_runtime.entrypoint:celery_app inspect ping --timeout 30   # dev
docker compose -f docker-compose.prod.yml -p kawaru-prod exec -T worker \
  celery -A celery_runtime.entrypoint:celery_app inspect ping --timeout 30   # prod
```

## 5. healthcheck 说明

dev / prod 一致：只给 `app`(`/docs`) + `mariadb` + `redis` 做 healthcheck；`worker`/`beat` **不做**：
- beat 是调度器，不响应 control 命令，`inspect ping` 永不通过；
- worker 的 `inspect ping` 每次会冷启动整套 app 而超时。

二者存活由 `restart: unless-stopped` 兜底。`docker compose up --wait` 因此只等 app 健康 + worker/beat 起来，不会卡死。

## 6. GitHub Secrets

| 名称 | 用途 |
|---|---|
| `DEV_SSH_HOST` / `DEV_SSH_USER` / `DEV_SSH_KEY` | 独立 dev 服务器（22 端口） |
| `PROD_SSH_HOST` / `PROD_SSH_USER` / `PROD_SSH_KEY` | **独立 prod 服务器**（22 端口），与 dev 的 `DEV_SSH_*` 分开 |
| `GHCR_PULL_USER` | GitHub 用户名（小写），CD SSH 到服务器后用它登录 GHCR 拉私有镜像（dev / prod 共用） |
| `GHCR_PULL_TOKEN` | PAT（classic，scope 只勾 `read:packages`），与 `GHCR_PULL_USER` 配套（dev / prod 共用） |

DB/Redis/OSS/SMTP 等业务凭证都在服务器 `.env` 里，**不进 GitHub Secrets**。

## 7. dev / prod 对照

| 维度 | dev | prod（正式发布） |
|---|---|---|
| 触发分支 | `dev` | `main` |
| Workflow | [dev-cd.yml](../../.github/workflows/dev-cd.yml) | [prod-cd.yml](../../.github/workflows/prod-cd.yml) |
| 镜像 tag | `dev-latest` + `dev-<sha>` | `latest` + `sha-<sha>` |
| 服务器 secrets | `DEV_SSH_*` | `PROD_SSH_*` |
| 服务器目录 | `/opt/kawaru-dev` | `/opt/kawaru-prod` |
| compose project | `kawaru-dev` | `kawaru-prod` |
| compose 文件 | `docker-compose.dev.yml` | `docker-compose.prod.yml` |
| 配置文件 | `dev-config.yaml` | `prod-config.yaml` |
| DB/Redis 端口 | 暴露 `0.0.0.0:13306/16379`（便于外部检测） | 仅 `127.0.0.1:13306/16379`（不对公网开放） |
| 并发抢占 | `cancel-in-progress: true` | `cancel-in-progress: false`（不中断发布） |
