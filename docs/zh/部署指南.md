# 部署指南（dev / prod）

push 到 `dev` / `main` 分支后，[.github/workflows/dev-cd.yml](../../.github/workflows/dev-cd.yml) / [.github/workflows/prod-cd.yml](../../.github/workflows/prod-cd.yml) 自动：
**构建镜像 → 推 ACR（香港私有仓库 `kawaru/kawaru`）→ SSH 到对应服务器同步 compose → 备份数据库（prod）→ 启动基础组件 → 执行 migrate 容器升级 → `up -d --wait` 启动应用 → 刷新本地 `dev-latest` / `latest` 标签并清理 7 天前的旧镜像**。部署失败时会自动输出 6 个服务（包括 migrate）的状态与日志摘要，无需人工 SSH 翻日志。

两个 CD **只做构建与部署**，不生成/修改任何密钥或配置。`.env` 与 `{dev,prod}-config.yaml` 由人一次性准备在服务器上，之后归你维护。

> **dev 与 prod 互不影响**：dev 跟 `dev` 分支、镜像 `dev-latest`、服务器 `/opt/kawaru-dev`、项目名 `kawaru-dev`；prod 跟 `main` 分支、镜像 `latest`、**独立的另一台 prod 服务器** `/opt/kawaru-prod`、项目名 `kawaru-prod`。两套互不影响。详见文末对照表。

> **镜像仓库已从 GHCR 迁到香港 ACR**：私有仓库 `crpi-y6a776c9l4k3agmh.cn-hongkong.personal.cr.aliyuncs.com/kawaru/kawaru`，服务器拉取镜像不再需要开代理。域名按位置分三种用法：GitHub runner 构建推送、dev 服务器（杭州）拉取都用**公网域名**；prod 服务器（香港）拉取用 **`-vpc` 内网域名**（同地域内网，更快且不耗公网流量）。docker 按域名认证，登录与拉取必须用同一域名。ACR 个人版拒绝 OCI attestation manifest，工作流已固定 `provenance: false` + `sbom: false`。

## 1. 架构（Celery 分离模式 + 独立 Migrate 容器）

```
mariadb  ─┐
redis   ──┼─ migrate (一次性升级) ──> app(8000)
          ├─ worker (celery -Q default)
          └─ beat   (celery 调度)
```

- `enable_embedded_celery: false`，app 不再 fork worker/beat；worker、beat 各自独立容器。
- 数据库变更由独立的 One-Shot `migrate` 容器执行；`app`、`worker`、`beat` 均显式声明等待 `migrate` 成功完成（`condition: service_completed_successfully`）。
- 端口：app `8000`

**dev vs prod 关键区别：**

| 项目 | Dev | Prod |
|------|-----|------|
| mariadb/redis 端口 | 暴露 `0.0.0.0:13306/16379`（便于外部检测） | 仅绑定 `127.0.0.1:13306/16379`（不对公网开放） |
| 外部访问 | 直接连服务器 IP | 需 SSH 隧道 |

dev 可通过面板查看容器：<https://testpanel.neonexus.top/panel>

prod 可通过面板查看容器：https://panel.bionet.pro/login

## 2. 服务器一次性准备

dev / prod 命令结构完全相同，只有目录名、配置名不同。两台机器各跑一遍。

```bash
# 先设置环境变量（根据实际环境修改）
export ENV_NAME=dev   # 或 prod

# 1) 创建目录（prod 会在部署时自动在 data/backups 存放数据库快照）
sudo mkdir -p /opt/kawaru-${ENV_NAME}/data/{mariadb,redis,backups,logs/{app,worker,beat}}
cd /opt/kawaru-${ENV_NAME}

# 2) 顶层目录交给 SSH 登录用户（CD 用该用户 scp compose 文件）
#    若顶层是 root:root，drone-scp 会在 tar 步骤报 Permission denied
sudo chown -R "$USER":"$USER" /opt/kawaru-${ENV_NAME}

# 3) app/worker/beat 以 appuser(默认 uid 1000) 运行，给日志目录授权
sudo chown -R 1000:1000 /opt/kawaru-${ENV_NAME}/data/logs

# 4) 放配置文件
#    .env 中需有 CONFIG_PATH=/app/config/${ENV_NAME}-config.yaml
#    配置文件命名为 ${ENV_NAME}-config.yaml
```

容器内配置必须使用 Compose 服务地址：`database.host=mariadb`、`database.port=3306`、`database.db_name=kawaru`，以及 `redis.host=redis`、`redis.port=6379`；同时保持 `celery.enable_embedded_celery=false`。宿主机映射端口 `13306` / `16379` 只用于从容器外访问，不能写进容器内连接配置。

**目录结构示例：**

```
/opt/kawaru-${ENV_NAME}/
├── .env                    # 环境变量，含 CONFIG_PATH
├── ${ENV_NAME}-config.yaml # 应用配置
├── docker-compose.${ENV_NAME}.yml  # CD 自动同步
└── data/
    ├── mariadb/
    ├── redis/
    └── logs/
        ├── app/
        ├── worker/
        └── beat/
```

之后每次 push `dev` / `main` 都会自动拉取并重建对应应用容器。数据库、Redis 与日志保留在宿主机，业务文件保留在 OSS。

服务器 `.env` 至少应包含 compose 和应用启动所需的 `APP_IMAGE`、`DATABASE_PASSWORD`、`REDIS_PASSWORD`、`SECRET_KEY`、`SMTP_PASSWORD`、`CONFIG_PATH`、`REGION_PATH`、`LOG_DIR`、`LOG_LEVEL`、OSS 凭证、FC 调用令牌及 `FC_CALLBACK_TOKEN`。CD 部署时会临时用本次 commit 镜像覆盖 `APP_IMAGE`；保留一个 `dev-latest` / `latest` 值便于人工执行 compose 命令。

## 3. 落盘清单（bind mount → 本地）

以下数据都存储到宿主机器硬盘上，不在容器里面。dev / prod 布局一致。

| 内容 | 容器内 | 宿主机 |
|---|---|---|
| MariaDB | `/var/lib/mysql` | `data/mariadb` |
| Redis(AOF) | `/data` | `data/redis` |
| app 日志 | `/app/kawaru_logs` | `data/logs/app` |
| worker 日志 | `/app/kawaru_logs` | `data/logs/worker` |
| beat 日志 | `/app/kawaru_logs` | `data/logs/beat` |

> 日志按服务拆分到不同目录：避免 app/worker/beat 三个进程同时写同名文件导致 `RotatingFileHandler` 轮转冲突。

应用容器不再挂载业务文件目录。上传 ZIP、解包后的 imZML/ibd、图像、下载压缩包以及处理产生的 Zarr 全部存放在 OSS。

## 4. OSS 与 FC 前置配置

当前服务仅支持 OSS。首次部署前需完成以下配置：

- 在 `{dev,prod}-config.yaml` 中配置 OSS `region_id`、`bucket_name`、对象根目录（`oss_zip_storage_root`、`oss_origin_storage_root`、`oss_processed_storage_root`），以及各 FC 的端点和超时。
- 在 `.env` 中配置 `OSS_ACCESS_KEY_ID`、`OSS_ACCESS_KEY_SECRET`、`OSS_ROLE_ARN`、五个 `OSS_FC_*_TOKEN`（algorithm、TIC、feature、raw-convert、clustering）和 `FC_CALLBACK_TOKEN`。
- 为长期 OSS 身份授予后端所需的最小权限（包括扮演配置的角色以及管理、标记对象），并正确配置 RAM 角色，使应用能向客户端签发代码生成的限定路径上传/下载 STS 策略。
- 配置 OSS 上传事件触发解包 FC。上传对象键是 `{oss_zip_storage_root}/{file_verify_code}/{file_id}.zip`；FC 需从文件名解析 `file_id`，把 imZML/ibd 写到 `{oss_origin_storage_root}/{file_verify_code}/{file_id}/` 下，并在 `X-FC-Token` 中携带同一个 `FC_CALLBACK_TOKEN`，以 `file_id` 回调 `/callback/oss_upload_callback`。
- 其他 FC 函数也必须携带 `X-FC-Token` 调用各自的 `/callback/*` 路由。feature/UMAP 结果回调 `/callback/umap_callback`，TIC 回调 `/callback/tic_callback`；图像回调的 `image_path` 是预览图所在目录的对象键（以 `/` 结尾，如 `images/{public_id}/`），不含具体文件名。FC 必须能访问回调地址，app/worker 容器必须能出站访问 OSS、STS 与全部 FC 端点（STS 凭证由 app 进程直接签发）。
- 配置 OSS 生命周期规则，回收始终未获得 `persistent=true` 标签的遗留对象；该规则不能误删已标记的源文件和解包文件。

对象位置由配置控制，不依赖宿主机目录：

| 内容 | OSS 位置 |
|---|---|
| 上传 ZIP | `{oss_zip_storage_root}/{file_verify_code}/{file_id}.zip` |
| 解包后的 imZML/ibd | `{oss_origin_storage_root}/{file_verify_code}/{file_id}/{原始文件名}.imzML/.ibd` |
| 算法/RAW 直转 Zarr | `{oss_processed_storage_root}/run_{run_id}.zarr/` |
| 聚类结果 | 写回对应 run 的 Zarr，不创建第二个输出目录 |
| TIC/UMAP 预览图 | `images/{public_id}/` 目录（FC 回调该目录键；TIC 写 `preview.jpg`，UMAP 写 `preview.jpg`/`preview_2.jpg`/`preview_3.jpg`） |

> `/docs` 健康只说明 API 及基础依赖已启动。正式接流量前至少完成一次端到端冒烟：预检 → STS 上传 → 解包回调 → RAW 签名下载；若客户端会使用中转下载与处理功能，还应分别验证一次中转下载和处理回调。

## 5. 常用运维

**dev 代理说明：** dev 触发任务前需开代理，触发后关闭，然后重启容器。prod 不需要。
参见：<https://github.com/nelvko/clash-for-linux-install>

```bash
# 先设置环境变量（根据实际环境修改）
export ENV_NAME=dev   # 或 prod
export APP_IMAGE=crpi-y6a776c9l4k3agmh.cn-hongkong.personal.cr.aliyuncs.com/kawaru/kawaru:dev-latest    # dev
# export APP_IMAGE=crpi-y6a776c9l4k3agmh-vpc.cn-hongkong.personal.cr.aliyuncs.com/kawaru/kawaru:latest  # prod

cd /opt/kawaru-${ENV_NAME}

# 查看配置 / 密码
cat .env

# 查看管理员密码（首次启动时在日志中打印，重启不会重打）
sudo grep -rE "create admin user|user already exists" /opt/kawaru-${ENV_NAME}/data/logs/app/

# 查看日志（把末尾 service 名换成 app / beat / mariadb / redis / migrate）
docker compose -f docker-compose.${ENV_NAME}.yml -p kawaru-${ENV_NAME} logs -f worker

# 改了 .env / ${ENV_NAME}-config.yaml 后强制重建应用容器
docker compose -f docker-compose.${ENV_NAME}.yml -p kawaru-${ENV_NAME} up -d --force-recreate app worker beat

# 确认 worker 已连上 broker（一次性检查，勿放进 healthcheck）
docker compose -f docker-compose.${ENV_NAME}.yml -p kawaru-${ENV_NAME} exec -T worker \
  celery -A celery_runtime.entrypoint:celery_app inspect ping --timeout 30

# 手动执行数据库迁移与校验（详见 [数据库迁移指南](数据库迁移指南.md)）
docker compose -f docker-compose.${ENV_NAME}.yml -p kawaru-${ENV_NAME} run --rm migrate \
  python -m database.migration upgrade
docker compose -f docker-compose.${ENV_NAME}.yml -p kawaru-${ENV_NAME} run --rm migrate \
  python -m database.migration verify
```

**外部检测 DB / Redis：**

```bash
# dev：直接连服务器 IP
mysql  -h <服务器IP> -P 13306 -uroot -p
redis-cli -h <服务器IP> -p 16379 -a <REDIS_PASSWORD> ping

# prod：先开 SSH 隧道再连本地端口
ssh -L 13306:127.0.0.1:13306 -L 16379:127.0.0.1:16379 <PROD_SSH_USER>@<服务器IP>
mysql  -h 127.0.0.1 -P 13306 -uroot -p
redis-cli -h 127.0.0.1 -p 16379 -a <REDIS_PASSWORD> ping
# 数据库密码 / Redis 密码都在 .env 里
```

## 6. healthcheck 说明

dev / prod 一致：只给 `app`(`/docs`) + `mariadb` + `redis` 做 healthcheck；`worker`/`beat` **不做**：
- beat 是调度器，不响应 control 命令，`inspect ping` 永不通过；
- worker 的 `inspect ping` 每次会冷启动整套 app 而超时。

二者存活由 `restart: unless-stopped` 兜底。`docker compose up --wait` 因此只等 app 健康 + worker/beat 起来，不会卡死。

## 7. GitHub Secrets

| 名称 | 用途 |
|---|---|
| `DEV_SSH_HOST` / `DEV_SSH_USER` / `DEV_SSH_KEY` | 独立 dev 服务器（22 端口） |
| `PROD_SSH_HOST` / `PROD_SSH_USER` / `PROD_SSH_KEY` | **独立 prod 服务器**（22 端口），与 dev 的 `DEV_SSH_*` 分开 |
| `ACR_USERNAME` | ACR 登录用户名（当前为 `NeoNexus`），CI 推送镜像与 CD SSH 到服务器后拉取私有镜像共用（dev / prod 共用） |
| `ACR_PASSWORD` | ACR“访问凭证”页设置的固定密码，与 `ACR_USERNAME` 配套（dev / prod 共用） |
| `OSS_ACCESS_KEY_ID` / `OSS_ACCESS_KEY_SECRET` / `OSS_ROLE_ARN` | CI 集成测试访问测试 Bucket 与签发 STS |
| `SMTP_PASSWORD` | CI 的并发注册和密码重置测试 |

dev/prod 运行时使用的 DB/Redis/OSS/FC/SMTP 凭证保存在各自服务器 `.env` 中；GitHub Secrets 中的 OSS/SMTP 项只供 CI 测试资源使用。完整清单见 [secrets.example.yaml](../../secrets.example.yaml)。

## 8. dev / prod 对照

| 维度 | dev | prod（正式发布） |
|---|---|---|
| 触发分支 | `dev` | `main` |
| Workflow | [dev-cd.yml](../../.github/workflows/dev-cd.yml) | [prod-cd.yml](../../.github/workflows/prod-cd.yml) |
| 镜像 tag | `dev-latest` + `dev-<sha>` | `latest` + `sha-<sha>` |
| 镜像仓库 | ACR 香港 `kawaru/kawaru`，拉取用公网域名 | 同左，拉取用 `-vpc` 内网域名 |
| 服务器 secrets | `DEV_SSH_*` | `PROD_SSH_*` |
| 并发抢占 | `cancel-in-progress: false`（不中断发布） | `cancel-in-progress: false`（不中断发布） |
