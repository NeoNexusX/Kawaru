# 贡献指南

## 快速开始

1. 克隆仓库并同步最新 `test` 分支
2. `uv sync` 安装依赖
3. 从 `test` 创建功能分支，开发完成后提交 PR

## 分支策略

```
main  ← merge commit ← dev  ← merge commit ← test  ← squash merge ← feature/*
```

| 分支 | 用途 | 合并方式 |
|------|------|----------|
| `feature/*` | 个人功能分支 | 向主仓库test提交 |
| `test` | 集成测试 | feature → test：**Squash and merge**，合并后删除功能分支 |
| `dev` | 验收 | test → dev：**Create a merge commit** |
| `main` | 生产 | dev → main：**Create a merge commit** |

test/dev/main 之间用 merge commit 而非 squash，避免丢失中间提交历史导致后续 PR 重复显示已合入的提交。

## 提交流程

### 1. 开始新任务

```bash
git checkout test
git pull origin test
git checkout -b feature/<topic>
```

### 2. 提交 PR

- **feature → test**：Squash and merge，合并后删除功能分支
- 标题遵循 Conventional Commits：`feat(file): support oss upload`
- 描述包含关键改动、影响范围、`Closes #<id>`

### 3. 多人协作同步

别人 PR 合并后，同步最新 test 再继续：

```bash
git fetch origin
git rebase origin/test   # 推荐，保持线性历史
# 或 git merge origin/test
```

### 4. 向上合并

测试通过后：test → dev → main，均提交 Create a merge commit PR。push 到 `dev` / `main` 会自动触发部署（见 [部署指南](部署指南.md)）。

## 提交信息规范

使用 Conventional Commits：`feat` / `fix` / `docs` / `refactor` / `test`

## 命名规范

| 类型 | 风格 | 示例 |
|------|------|------|
| 文件/函数/变量 | `snake_case` | `user_api.py`, `create_user` |
| 类 | `PascalCase` | `UserInDB`, `UserPublic` |
| 常量 | `UPPER_CASE` | `SECRET_KEY` |
| 布尔变量 | `is_`/`has_` 前缀 | `is_active` |
| 依赖注入 | `get_` 前缀 | `get_db` |

模型命名：`UserBase`（共享字段）、`UserInDB`（数据库）、`UserPublic`（响应）、`UserCreate`/`UserUpdate`（请求）。

所有函数参数和返回值必须添加类型注解。项目运行时要求 Python 3.12+，类型写法使用 `|` 代替 `Union`。

## CI 与代码检查

push 到 `test` 分支触发 CI（[.github/workflows/ci.yml](../../.github/workflows/ci.yml)），包含四个顺序执行的阶段：

1. **数据库迁移门禁（`migration-check`）**：在 GitHub runner 启动一次性 MariaDB 服务，依次执行：
   - `check-heads`：校验 Alembic 迁移仅有单个 Head（防止多分支未合并冲突）
   - `upgrade` + `verify` + `alembic check`：在临时空库构建最新结构，并比对 SQLModel 与 DDL 的 100% 一致性
   - `test-upgrade-from-previous`：测试从上一版本平滑增量升级
   - 运行 `tests/migrations/` 数据迁移单元测试
2. **静态检查（`static-checks`）**：`uv sync --frozen` 校验锁文件 → `compileall` 语法检查 → `uvx ruff check .` lint（当前不阻塞，存量 lint 清完后转为强制）
3. **构建镜像（`build-image`）**：静态检查通过后，构建测试镜像并推送到 GHCR
4. **集成测试（`integration-test`）**：在 GitHub runner 上用 [docker/docker-compose.test.yml](../../docker/docker-compose.test.yml) 起完整测试栈（migrate + app 9001 + celery-worker + celery-beat + mariadb + redis），容器内执行 `pytest -m "oss or perf_concurrent or password_reset"`（依赖 OSS / SMTP secrets）

提交 PR 前建议本地至少跑一遍：

```bash
uv run python -m database.migration check-heads
uv run python -m database.migration upgrade
uv run python -m database.migration verify
uv run alembic check
uv run pytest -c pytest.ini --confcutdir=tests/migrations tests/migrations -q
uv run python -m compileall -q .
uv run pytest --collect-only -q
uvx ruff check .
```

若对应外部服务可用，还应执行与改动相关的测试 marker。

> pylint 不在 CI 流程中；如需本地使用，注意 [.pylintrc](../../.pylintrc) 的 max-line-length 为 150。

## 运行测试

测试是端到端的（依赖运行中的服务 + MariaDB + Redis + celery worker），有两种跑法。

### 方式一：仓库 Actions（推荐）

CI 在代码进入 `test` 分支后自动运行，也可以在 Actions 页面通过 `workflow_dispatch` 手动触发。不要为了跑 CI 把个人功能分支强推覆盖共享 `test` 分支。

> 集成测试需要在仓库 **Settings → Secrets and variables → Actions** 配置 `OSS_ACCESS_KEY_ID` / `OSS_ACCESS_KEY_SECRET` / `OSS_ROLE_ARN` / `SMTP_PASSWORD` 四个 secrets（完整清单见根目录 [secrets.example.yaml](../../secrets.example.yaml)）；缺失时 integration-test 阶段会直接失败，静态检查与镜像构建不受影响。

### 方式二：本地运行

必须连接一个**正在运行**的服务（地址由 `.env` 的 `BASE_URL` 指定，默认 `http://127.0.0.1:8000`）：

1. 按 README 起好本地服务（含 celery worker，否则邮件类任务不会执行）
2. `.env` 中配置 `TEST_USER` / `TEST_PWD`；留空则 conftest 自动从 `kawaru_logs/api.log` 解析首次启动时打印的管理员账号
3. 运行 `uv run pytest`（可用 `-m oss` 等 marker 筛选，marker 定义见 [pytest.ini](../../pytest.ini)）

也可以用测试栈整体跑（与 CI 一致，端口 9001，跑完即销）：

```bash
docker compose -f docker/docker-compose.test.yml -p kawaru-test up -d --build --wait
docker compose -f docker/docker-compose.test.yml -p kawaru-test exec -u root app sh -lc 'mkdir -p /test_temp && chown -R appuser /test_temp'
docker compose -f docker/docker-compose.test.yml -p kawaru-test exec -T app python -m pytest -m "oss or perf_concurrent or password_reset" -q
docker compose -f docker/docker-compose.test.yml -p kawaru-test down -v
```

各 marker 的外部依赖如下：

- `oss` 使用真实 Bucket，覆盖预检 → 受限 STS → OSS 直传 → 等待事件触发的 FC 解包 → 模拟带鉴权的上传回调 → RAW 签名下载与 MD5 校验 → 清理。它需要 OSS 凭证、正确的 Bucket 事件以及可用的解包 FC。测试会在解包完成后自行模拟回调，不会等待 FC 自动回调 API。
- `password_reset` 需要可用的 `SMTP_PASSWORD`；`perf_concurrent` 不发邮件，测试进程直接为每个账号的邮箱签发注册验证码（验证码与邮箱绑定），因此需要与服务端连接同一个 Redis。

当前 OSS 测试尚未验证 FC 自动回调投递、TIC/UMAP 回调产物、ZIP 打包、算法/RAW 直转/聚类任务、失败重试以及多用户竞态。修改这些链路时应补充对应测试；仅 `oss` marker 通过不能证明整套 OSS/FC 部署已经完整可用。

## PR 评审清单

- 涉及模型变更时已生成对应的 Alembic 迁移脚本，并通过了单 Head 及迁移测试校验
- 命名规范、模块边界、接口约定一致
- 无明显性能/内存问题
- 错误处理到位，边界情况覆盖
- 文档同步更新
- 测试通过且覆盖关键逻辑
